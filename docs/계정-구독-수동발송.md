# 계정, 개인 구독과 수동 이메일 운영

확인일: 2026-10-21. 구현과 외부 서비스 연결은 별도 상태다.

## 확정한 사용자 동작

- GitHub 로그인으로 가입하고 계정별 공개 저장소 구독을 저장한다.
- 공개 레포 탐색, 공용 레포 등록, 이슈 조회는 로그인 없이 유지한다. 개인 기여 기록은 로그인해야 저장한다.
- 알림 이메일은 사용자가 직접 입력한다. `수동 이메일 알림 받기`를 선택한 계정만 발송 대상이다.
- 운영자가 이메일을 수동 발송한다. 코드에 SMTP 연결이나 자동 발송 예약은 없다.
- 한 사람에게 하루 최대 3개 이슈를 담는다. 날짜 경계는 한국시간이다.
- 매일 11시는 제안이며 확정된 스케줄이 아니다.
- 현행 v2 등급은 본문 구체성이다. 성공 횟수에 따른 난이도 상향으로 해석하지 않는다.

정상 흐름은 공개 탐색 -> GitHub 로그인 -> 저장소 구독/이메일 수신 설정 저장 -> 재조회 확인이다.
로그인 전 입력은 현재 브라우저의 sessionStorage에 보관했다 돌아오면 복원하며 자동 저장하지 않는다.
저장 실패와 인증 만료 시 입력을 보존하고 성공으로 표시하지 않는다. 로그아웃 시 개인 설정 표시를 비운다.
입력 이메일의 소유권 확인은 구현하지 않았다. 자동 확인 메일을 보냈다고 표시하지 않는다.

## 외부 설정

사용자는 기존 Upstash DB와 GitHub OAuth App을 사용하고 비밀 설정을 직접 입력하기로 했다.
설정 화면: [Vercel 프로젝트](https://vercel.com/dashboard), [GitHub OAuth Apps](https://github.com/settings/developers), [Upstash 콘솔](https://console.upstash.com/).

GitHub OAuth App의 callback은 아래 고정 주소다.

```text
https://repobite.vercel.app/api/account?action=callback
```

Vercel 운영 환경에 다음 이름을 설정한다. 실제 값은 비밀 설정 화면 또는 대화형 보안 입력으로만 전달한다.

- `GITHUB_OAUTH_CLIENT_ID`
- `GITHUB_OAUTH_CLIENT_SECRET`
- `UPSTASH_REDIS_REST_URL`
- `UPSTASH_REDIS_REST_TOKEN`

Windows 배치 실행 계정에는 같은 Upstash DB의 두 환경변수를 설정한다.
서버에서 GitHub 로그인 콜백을 처리하지 않으므로 Windows 배치에 OAuth client secret은 필요하지 않다.
운영 연결 순서는 [Windows 운영](Windows-운영.md)을 따른다.

확인 당시 Vercel 운영 환경변수는 비어 있었고 Windows의 User/Machine에도 DB 설정이 없었다.
코드가 있어도 이 상태에서 실제 로그인, 개인 구독 저장과 공용 결과 반영은 완료되지 않는다.

GitHub OAuth는 state 대조와 PKCE S256을 사용하고 로그인마다 `/user`로 신원을 확인한다.
GitHub 토큰은 신원 확인에만 사용하고 DB에 보관하지 않는다. 세션은 임의 값의 해시 키로 저장하며 30일 만료다.
쿠키는 Secure, HttpOnly, SameSite=Lax이고 state는 10분 후 만료된다.
콜백의 code/state를 애플리케이션 액세스 로그에 쓰지 않는다.
구현 근거: [GitHub OAuth 웹 흐름](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps).

## API와 공개 범위

`/api/account?action=session`은 비로그인 시 `{authenticated:false}`를 반환한다.
로그인 시 본인의 GitHub 신원, 이메일 수신 설정, 구독만 반환한다.
`start`, `callback`, `logout`, `preferences`, `subscriptions`는 같은 계정 API가 처리한다.
설정 변경과 구독/해지는 세션, 정식 운영 Origin과 `expected_user_id`를 검증한다.
다른 탭에서 GitHub 계정을 바꿨으면 저장 전에 409로 거절하며 다른 계정에 입력을 저장하지 않는다.

개인 구독은 공용 레포 등록과 별도 저장한다. 공용 배치는 기본 목록, 공용 등록, 개인 구독 저장소를
대소문자 정규화해 합친다. 공개 결과에는 저장소와 이슈만 포함하며 계정 ID와 이메일을 넣지 않는다.
공개 변환은 `public_feed.py`에서 담당한다. 배치가 웹 서버 모듈을 가져오지 않는다.
현재 `web.Application`은 상태, 프로세스, 파일 저장을 함께 맡는 단일 책임 원칙 위반이 남아 있다.
이번 변경은 공개 변환 의존 경계만 분리했다.

## 수동 발송 절차

배치 성공 후 운영자 전용 환경에서 초안을 생성한다. 아래 경로는 환경변수 참조이며 실제 개인 경로를 문서에 저장하지 않는다.
생성한 SQLite와 `.eml`에는 이메일이 있으므로 Git과 Vercel 공개 파일 밖에 보관한다.

```powershell
py -3.14 manual_delivery.py --state "$env:LOCALAPPDATA\RepoBite\private\delivery.sqlite" prepare --input .radar-community\candidates.jsonl --output "$env:LOCALAPPDATA\RepoBite\private\drafts"
```

초안 생성은 메일을 보내지 않는다. 현행 모델/기준의 후보만 소비하고 공개 상태와 GitHub 최신성을 다시 확인한다.
구독 저장소와 일치하는 미발송 이슈를 한국시간 하루 최대 3건 담아 `.eml`을 만든다.
본문 완결성 등급이라는 설명과 한국어 판정 이유를 포함한다. 이유는 줄바꿈을 제거하고 40자로 제한한다.
같은 사람/이슈의 운영자 확인 기록이 있으면 다음 날에도 다시 담지 않는다.
동일 날짜 초안 재생성은 새 발송 기록이 아니며 무효 후보는 제외된다.
매번 전체 수신 목록을 다시 읽어 미발송 초안을 재작성한다. 수신 거부·구독 해지 계정과 지난 날짜의
대기 초안은 재사용하지 않는다. 지정한 출력 폴더에서 이전 자동 생성 `.eml`을 정리하고 새 초안만 남긴다.

운영자가 새로 생성한 초안과 수신 주소를 확인하고 직접 메일을 보낸 뒤 해당 초안 ID를 기록한다.

```powershell
py -3.14 manual_delivery.py --state "$env:LOCALAPPDATA\RepoBite\private\delivery.sqlite" confirm-sent 초안ID
```

이 기록은 `operator_confirmed`다. 제공자의 전송 성공이나 수신자의 도착 확인을 뜻하지 않는다.
발송에 실패했으면 확인하지 않고 새 초안 생성부터 재시도한다. 여러 수신자 중 성공한 초안만 개별 확인한다.
당일 초안만 확인할 수 있고 같은 확인 요청은 중복 기록하지 않는다. 프로세스 재시작 후에도 기록은 유지한다.
수동으로 복사한 메일과 오래된 `.eml`을 코드가 회수할 수는 없다. 실제 보내기 직전 초안을 다시 생성해야 한다.
클릭, 착수, PR 생성과 병합은 이 발송 기록에 포함하지 않는다.

발송 확인과 로컬 outbox 기록은 같은 SQLite 트랜잭션으로 저장한다. 이후 같은 Upstash DB에
동기화하며, 실패하면 로컬 확인을 보존하고 다음 명령으로 기록만 재시도한다. 메일은 다시 보내지 않는다.

```powershell
py -3.14 manual_delivery.py --state "$env:LOCALAPPDATA\RepoBite\private\delivery.sqlite" sync
```

동일 초안 ID는 원격에서도 한 번만 저장하며, 원격 저장 후 응답이 유실돼도 재시도할 수 있다.
원격 전달 기록에는 이메일과 본문을 저장하지 않고 이슈 키, 확인 시각과 운영자 확인 근거만 둔다.
받는 주소나 메일 내용이 바뀌면 새 초안 ID가 되어 이전 초안을 확인할 수 없다.

## 개인 기여 기록

| 행동·조건 | 화면 결과 | 저장 상태 |
| --- | --- | --- |
| 공개 이슈에서 기여 기록 열기 | 이슈를 선택한 개인 기록 창 | 열기만으로 저장하지 않음 |
| 비로그인 착수·PR 연결 | GitHub 로그인 안내, 입력 유지 | 저장하지 않음 |
| 로그인 후 착수·취소·재개 | 현재 상태를 재조회해 표시 | 계정별 활동 이벤트 |
| 내 PR 주소 연결·병합 확인 | GitHub 근거와 병합 상태 표시 | 본인 공개 PR만 저장 |
| 실패·계정 변경 | 성공 표시 없이 재시도·로그인 확인 안내 | 이전 기록 보존, 다른 계정에 저장하지 않음 |
| 운영자 확인 전달 선택 | 같은 이슈의 본인 전달 기록만 선택 | 명시한 활동에만 전달 ID 연결 |

`GET /api/contributions?expected_user_id=현재계정ID`는 본인의 기록, 운영자 확인 전달 목록과 집계를 반환한다.
`POST /api/contributions?action=start|cancel|resume|submit_pr|verify_pr`는 세션, 정식 Origin,
`expected_user_id`와 요청별 `event_id`를 검증한다. 전달 연결은 본인에게 실제 기록된 같은 이슈만 허용한다.
신규 기록은 공개 저장소의 실제 이슈인지 확인한다. 착수는 RepoBite의 개인 활동 기록이며 GitHub 담당자 지정은 아니다.

PR은 같은 저장소를 대상으로 하고 로그인한 GitHub 숫자 ID가 작성자인 공개 PR만 저장한다.
GitHub의 `merged_at`과 병합 상태를 확인한 고유 PR URL 수를 성공으로 집계한다.
이슈와 PR의 연결은 사용자 신고이며 해당 PR이 이슈를 닫았다고 추정하지 않는다.
동일 이벤트 재전송은 저장된 응답을 반환하므로 화면은 변경 뒤 GET으로 현재 상태를 재조회한다.
취소와 재개는 활동 상태만 바꾸며 검증된 PR 병합 근거를 삭제하지 않는다.
성공 횟수에 따른 등급 자동 확장은 제외했다.

## 검증과 남은 연결

- 오프라인 검사: `python3.14 test_accounts.py`, `python3.14 test_manual_delivery.py`, `python3.14 test_community.py`, `node test_account_ui.mjs`.
- Mac Python 3.14 회귀 9개 파일, Node 공개 탐색 검사와 계정 UI 24개 테스트가 통과했다.
- 브라우저 모의 API로 익명 구독 로그인 유도, 개인 구독/해지, 이메일 저장·실패 입력 보존을 확인했다. 390px에서 페이지/대화상자 가로 넘침과 JavaScript 예외가 없었다.
- Windows 임시 폴더에서도 Python 9개 파일과 PowerShell 사전 검사가 통과했다. 실제 운영 폴더와 예약 작업은 변경하지 않았다. 이후 계정 전환 보호 수정은 Mac 계정/HTTP 13개·UI 24개 검사를 통과했다.
- 기여 UI는 계정 UI와 합쳐 Node 47개 검사 통과. 브라우저 모의 API에서 익명 로그인 유도, 착수·취소·재개·PR 연결과 병합 표시를 확인했다. 390px에서도 이슈와 개인 기록에 진입할 수 있고 가로 넘침·JavaScript 예외가 없었다.
- 실제 DB 저장, GitHub OAuth 왕복, Windows 공용 배치 실행, 수동 메일 발송은 별도 운영 증거가 필요하다.
- GitHub OAuth App과 DB 비밀 설정, 배포 후 정식 주소에서 로그인/구독/해지/이메일 저장을 확인해야 한다.
- 자동 알림, 새 발송 스케줄, 성장별 등급 확장은 제외했다. 실제 발송부터 PR까지의 전환 실측은 별도 사용자 흐름 증거가 필요하다.
