## Resend 자동 발송 (2026-10-26)

사용자는 자동 발송과 매일 한국 시간 오전 11시를 확정했다. 이 절은 아래 수동 발송 전용 정책과 11시 미확정 설명보다 우선한다.

- 발신자는 `RepoBite <notify@repobite.ao3921.com>`이다. 도메인 Verified는 사용자 확인이며 실제 API 접수·수신은 별도 검증한다.
- 수신 동의한 계정의 구독 저장소와 선택 난이도에 맞는 이슈만 하루 최대 3건 담는다. 후보가 없으면 보내지 않는다. 이메일 소유권 확인은 여전히 구현하지 않았으며 수신 동의를 인증 완료로 해석하지 않는다.
- 기존 `candidates.jsonl`은 Lv.1 전용이므로 자동 발송은 정기·즉시 수집의 전체 `grades.jsonl`에서 현재 snapshot과 일치하는 행을 읽는다. 최근 24시간 내 성공 snapshot, 현행 모델·기준·추론 설정, 공개 저장소와 GitHub의 닫힘·담당자·열린 PR 상태를 확인한다. 판정 이유·준비 상태는 메일에 넣지 않는다.
- 전송 직전 수신 동의·주소·구독·난이도를 재조회한다. 메일의 임의 토큰 링크는 로그인 없이 수신 해지를 지원한다. GET은 확인 화면만, POST는 해당 메일 주소의 동의만 원자적으로 해제한다. 주소가 바뀌면 이전 메일로 새 주소의 동의를 끌 수 없다. 토큰은 DB에 해시로 저장하고 1년 뒤 만료한다.
- 운영자 전용 기존 `%LOCALAPPDATA%\RepoBite\private\delivery.sqlite`를 재사용한다. 요청 본문·안정된 Idempotency-Key를 전송 전에 저장한다. 통신 중단은 같은 본문으로 재시도하고 23시간을 넘긴 미확인 요청이나 다른 날짜 요청은 보내지 않는다. 미확인 요청이 남은 계정의 새 초안도 차단한다. 해소하려면 Resend 로그에서 접수 여부를 대조해야 하며 DB 행을 임의로 삭제하고 다시 보내지 않는다.
- `provider_accepted`는 Resend API 접수 증거다. 실제 배달·수신 증거가 아니다. 수동 `operator_confirmed`와 구분하며 공유 DB 동기화 실패는 outbox에 남겨 메일을 재발송하지 않고 재시도한다. 같은 사용자의 이미 보낸 이슈와 같은 날 접수는 반복 발송하지 않는다.
- OS 파일 잠금과 예약 작업 `IgnoreNew`로 중복 실행을 막는다. 정기 수집과는 별도 `repobite-email` 작업이며 매일 11시, 실패 시 15분 간격 최대 3회 재시도, 최대 45분, 절전 복귀·누락 시 시작을 설정한다. 예약 실행과 수동 검증을 구분한다.

### 키 저장과 활성화

`scripts/configure-email.ps1`은 같은 Windows 예약 계정에서 키를 가려서 입력받고 DPAPI로 암호화해 Git 밖 `%LOCALAPPDATA%\RepoBite\resend-key.clixml`에 저장한다. 파일 ACL도 해당 계정으로 제한한다. 키를 User 환경변수나 명령 인자에 저장하지 않는다. `scripts/run-email.ps1`은 실행 프로세스에만 복호화한 키를 주입하고 종료 시 제거한다. Vercel에는 Resend 키가 필요 없다.

```bash
ssh -t home-server "powershell -NoProfile -ExecutionPolicy Bypass -Command \"Set-Location (Get-ScheduledTask repobite-web).Actions[0].WorkingDirectory; .\scripts\configure-email.ps1\""
```

입력 순서는 기존 Windows 작업 계정 암호, Resend 키, 확인 메일을 받을 본인 이메일이다. 공개키 SSH는 그대로 유지한다. 암호로 같은 계정의 Windows 로그온 토큰을 프로세스 안에서만 만들고 DPAPI CurrentUser 저장과 예약 등록에 사용한다. 암호를 명령 인자·파일로 전달하지 않으며 토큰과 입력은 종료 시 해제한다. 실제 키 입력 전 사용자 암호화 검사가 실패하면 중단한다. 확인 메일 접수 실패 시 예약 등록을 중단한다. 성공하면 다음 실행 시각을 출력한다. 비밀값을 채팅·명령 인자·문서에 붙이지 않는다. 재설정도 같은 명령을 사용한다.

진단은 `py -3.14 automatic_delivery.py --state <비공개 SQLite 경로> --dry-run`으로 전송 없이 준비만 확인한다. 기존 DB 파일을 복제하거나 다른 경로로 옮겨 발송하면 중복 방지 이력이 끊기므로 같은 상태 파일을 유지한다. 실행 시각과 종료 코드만 `email-runs.log`에 보관하고 수신자·요청·키는 로그에 남기지 않는다.

검증: `test_automatic_delivery.py`는 접수 후 재실행, 통신 중단·재시작 후 동일 본문·식별자 재사용, 오래된 미확인 요청 차단, 수신 설정 변경, 무후보·난이도 필터, Lv.2 즉시 수집 원본, OS 중복 잠금, 접수·수신 구분과 GET/POST 수신 해지 경계를 검사한다. 기존 계정·수동 초안·기여 기록 회귀도 실행한다. 실제 키 입력, 본인 메일 수신, 정규 11시 실행은 별도 운영 증거가 필요하다.

기존 `ManualDelivery`는 초안 구성·파일 출력·발송 기록을 함께 맡아 단일 책임 원칙 위반이 남아 있다. 이번 전송 책임은 `resend_delivery.py`, 자동 실행은 `automatic_delivery.py`, 수신 해지는 `email_optout.py`로 분리해 추가하지 않았다.

- 매일 11시는 제안이며 확정된 스케줄이 아니다.
- 현행 v2 등급은 본문 구체성이다. 성공 횟수에 따른 난이도 상향으로 해석하지 않는다.

정상 흐름은 공개 탐색 -> GitHub 로그인 -> 저장소 구독/이메일 수신 설정 저장 -> 재조회 확인이다.
로그인 전 입력은 현재 브라우저의 sessionStorage에 보관했다 돌아오면 복원하며 자동 저장하지 않는다.
저장 실패와 인증 만료 시 입력을 보존하고 성공으로 표시하지 않는다. 로그아웃 시 개인 설정 표시를 비운다.
입력 이메일의 소유권 확인은 구현하지 않았다. 자동 확인 메일을 보냈다고 표시하지 않는다.

## 외부 설정

사용자는 기존 GitHub OAuth App을 사용하며 Upstash DB는 새로 생성했다. 비밀 설정은 서비스 화면이나 숨김 입력으로만 다룬다.
설정 화면: [Vercel 프로젝트](https://vercel.com/dashboard), [GitHub OAuth Apps](https://github.com/settings/developers), [Upstash 콘솔](https://console.upstash.com/).

### 1. 기존 GitHub OAuth App 확인

[GitHub OAuth Apps](https://github.com/settings/developers)에서 RepoBite용 기존 앱을 연다.
개인 Settings -> Developer settings -> OAuth Apps에서도 접근할 수 있다.
Homepage URL은 `https://repobite.vercel.app`로, Authorization callback URL은 아래 고정 주소로 설정하고
Update application으로 저장한다. Client ID를 확인하고, 사용할 Client secret을 확보한다.
기존 secret을 확인할 수 없으면 Generate a new client secret으로 추가하되 다른 환경에서 사용 중인 secret을 임의로 삭제하지 않는다.

```text
https://repobite.vercel.app/api/account?action=callback
```

### 2. Upstash Redis 연결값 확인

[Upstash 콘솔](https://console.upstash.com/) -> Redis -> 생성한 RepoBite DB에서 Connect의 REST 연결 정보를 연다.
`UPSTASH_REDIS_REST_URL`의 HTTPS URL과 `UPSTASH_REDIS_REST_TOKEN`의 일반 읽기·쓰기 토큰을 사용한다.
Readonly Token이나 TCP 연결용 `redis://`/`rediss://` URL은 사용하지 않는다. 별도의 테이블 생성은 필요하지 않다.

### 3. Vercel Production에 네 값 입력

[Vercel 대시보드](https://vercel.com/dashboard) -> `repobite` 프로젝트 -> Settings -> Environment Variables에서
아래 이름을 그대로 추가하고 적용 환경은 Production으로 지정한다. 실제 값은 해당 화면에만 입력한다.

| 이름 | 값의 출처 | Windows에도 입력 |
| --- | --- | --- |
| `GITHUB_OAUTH_CLIENT_ID` | GitHub OAuth App의 Client ID | 아니요 |
| `GITHUB_OAUTH_CLIENT_SECRET` | 같은 앱의 Client secret | 아니요 |
| `UPSTASH_REDIS_REST_URL` | Upstash DB의 REST HTTPS URL | 예 |
| `UPSTASH_REDIS_REST_TOKEN` | 같은 DB의 읽기·쓰기 REST 토큰 | 예 |

프런트엔드용 접두사를 붙이지 않는다. 네 값을 저장한 뒤 새 Production 배포가 필요하다.
기존 배포에는 환경변수 변경이 소급 적용되지 않는다.

### 4. Windows 배치 계정에 DB 두 값 입력

홈서버에서 `repobite-batch`를 실행하는 Windows 계정으로 로그인한다.
시작 메뉴에서 **계정의 환경 변수 편집**을 찾아 열고, 사용자 변수 영역에
`UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN`을 새로 추가한다.
Vercel과 정확히 같은 DB의 값을 사용하며, 이름과 값은 각각 별도 입력란에 넣는다.
변수 값에 따옴표나 `이름=`을 덧붙이지 않는다. OAuth 두 값은 Windows 배치에 필요하지 않다.

현재 배치 wrapper는 실행 시 최신 User 환경변수를 읽으므로 기존 매일 03:00 작업을 다시 등록할 필요는 없다.
실제 공용 배치 성공은 별도 확인한다. 코드와 환경변수 저장만으로 로그인·DB 반영 완료로 판정하지 않는다.
검증 순서는 [Windows 운영](Windows-운영.md)을 따른다.

2026-10-23 사용자가 Vercel 설정과 재배포를 완료했다. 정식 운영 주소의 DB 읽기, 임시 OAuth 상태 쓰기, 실제 GitHub 로그인 왕복과 개인 목록 조회를 확인했다.
Windows에는 통합 코드와 DB 두 값의 User 환경변수 등록을 완료했다. 홈서버에서 운영 DB 읽기와 로그인 계정 저장을 확인했다.
Vercel Production Secret은 CLI로 다시 내려받지 못하므로 자동으로 복사하지 않았다. 사용자가 Mac의 숨김 입력 도구에 DB 두 값을 입력해 SSH로 Windows 사용자 환경변수에 전달했다. 입력값은 파일·명령 인자·로그에 기록하지 않으며 실제 DB 읽기·쓰기 성공 후 사용자 환경변수에 저장한다.
실제 개인 구독의 저장·새로고침 후 재조회·해지를 확인하고 원래 빈 구독 목록으로 복원했다. 이메일과 수신 동의는 변경하지 않았다.
Windows 공용 배치는 이슈 1,782건을 수집했지만 판정 100건 중 15건이 `429 RESOURCE_EXHAUSTED`로 실패해 종료 코드 1이었다. snapshot은 아직 없으며 종료 코드 0과 공개 반영은 미검증이다.

설정 화면 근거: [GitHub OAuth App 수정](https://docs.github.com/en/apps/oauth-apps/maintaining-oauth-apps/modifying-an-oauth-app),
[Upstash REST 연결](https://upstash.com/docs/redis/features/restapi),
[Vercel 환경변수](https://vercel.com/docs/environment-variables).

GitHub OAuth는 state 대조와 PKCE S256을 사용하고 로그인마다 `/user`로 신원을 확인한다.
GitHub 토큰은 신원 확인에만 사용하고 DB에 보관하지 않는다. 세션은 임의 값의 해시 키로 저장하며 30일 만료다.
쿠키는 Secure, HttpOnly, SameSite=Lax이고 state는 10분 후 만료된다.
콜백의 code/state를 애플리케이션 액세스 로그에 쓰지 않는다.
구현 근거: [GitHub OAuth 웹 흐름](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps).

## API와 공개 범위

`/api/account?action=session`은 비로그인 시 `{authenticated:false}`를 반환한다.
로그인 시 본인의 GitHub 신원, 이메일 수신 설정, 구독만 반환한다.
`start`, `callback`, `logout`, `preferences`, `subscriptions`는 같은 계정 API가 처리한다.
설정 변경과 구독/해지는 세션, 정식 운영 Origin과 `expected_user_id`를 검증한다.
다른 탭에서 GitHub 계정을 바꿨으면 저장 전에 409로 거절하며 다른 계정에 입력을 저장하지 않는다.

개인 구독은 공용 레포 등록과 별도 저장한다. 공용 배치는 기본 목록, 공용 등록, 개인 구독 저장소를
대소문자 정규화해 합친다. 공개 결과에는 저장소와 이슈만 포함하며 계정 ID와 이메일을 넣지 않는다.
공개 변환은 `public_feed.py`에서 담당한다. 배치가 웹 서버 모듈을 가져오지 않는다.
현재 `web.Application`은 상태, 프로세스, 파일 저장을 함께 맡는 단일 책임 원칙 위반이 남아 있다.
이번 변경은 공개 변환 의존 경계만 분리했다.

## 수동 발송 절차

배치 성공 후 운영자 전용 환경에서 초안을 생성한다. 아래 경로는 환경변수 참조이며 실제 개인 경로를 문서에 저장하지 않는다.
생성한 SQLite와 `.eml`에는 이메일이 있으므로 Git과 Vercel 공개 파일 밖에 보관한다.

```powershell
py -3.14 manual_delivery.py --state "$env:LOCALAPPDATA\RepoBite\private\delivery.sqlite" prepare --input .radar-community\candidates.jsonl --output "$env:LOCALAPPDATA\RepoBite\private\drafts"
```

초안 생성은 메일을 보내지 않는다. 현행 모델/기준의 후보만 소비하고 공개 상태와 GitHub 최신성을 다시 확인한다.
구독 저장소와 일치하는 미발송 이슈를 한국시간 하루 최대 3건 담아 `.eml`을 만든다.
저장소, 번호, 제목, Lv.1 쉬움·Lv.2 보통·Lv.3 어려움과 GitHub 링크만 소개하며 판정 이유·준비 상태는 표시하지 않는다.
같은 사람/이슈의 운영자 확인 기록이 있으면 다음 날에도 다시 담지 않는다.
동일 날짜 초안 재생성은 새 발송 기록이 아니며 무효 후보는 제외된다.
매번 전체 수신 목록을 다시 읽어 미발송 초안을 재작성한다. 수신 거부·구독 해지 계정과 지난 날짜의
대기 초안은 재사용하지 않는다. 지정한 출력 폴더에서 이전 자동 생성 `.eml`을 정리하고 새 초안만 남긴다.

운영자가 새로 생성한 초안과 수신 주소를 확인하고 직접 메일을 보낸 뒤 해당 초안 ID를 기록한다.

```powershell
py -3.14 manual_delivery.py --state "$env:LOCALAPPDATA\RepoBite\private\delivery.sqlite" confirm-sent 초안ID
```

이 기록은 `operator_confirmed`다. 제공자의 전송 성공이나 수신자의 도착 확인을 뜻하지 않는다.
발송에 실패했으면 확인하지 않고 새 초안 생성부터 재시도한다. 여러 수신자 중 성공한 초안만 개별 확인한다.
당일 초안만 확인할 수 있고 같은 확인 요청은 중복 기록하지 않는다. 프로세스 재시작 후에도 기록은 유지한다.
수동으로 복사한 메일과 오래된 `.eml`을 코드가 회수할 수는 없다. 실제 보내기 직전 초안을 다시 생성해야 한다.
클릭, 착수, PR 생성과 병합은 이 발송 기록에 포함하지 않는다.

발송 확인과 로컬 outbox 기록은 같은 SQLite 트랜잭션으로 저장한다. 이후 같은 Upstash DB에
동기화하며, 실패하면 로컬 확인을 보존하고 다음 명령으로 기록만 재시도한다. 메일은 다시 보내지 않는다.

```powershell
py -3.14 manual_delivery.py --state "$env:LOCALAPPDATA\RepoBite\private\delivery.sqlite" sync
```

동일 초안 ID는 원격에서도 한 번만 저장하며, 원격 저장 후 응답이 유실돼도 재시도할 수 있다.
원격 전달 기록에는 이메일과 본문을 저장하지 않고 이슈 키, 확인 시각과 운영자 확인 근거만 둔다.
받는 주소나 메일 내용이 바뀌면 새 초안 ID가 되어 이전 초안을 확인할 수 없다.

## 개인 기여 기록

| 행동·조건 | 화면 결과 | 저장 상태 |
| --- | --- | --- |
| 공개 이슈에서 기여 기록 열기 | 이슈를 선택한 개인 기록 창 | 열기만으로 저장하지 않음 |
| 비로그인 착수·PR 연결 | GitHub 로그인 안내, 입력 유지 | 저장하지 않음 |
| 로그인 후 착수·취소·재개 | 현재 상태를 재조회해 표시 | 계정별 활동 이벤트 |
| 내 PR 주소 연결·병합 확인 | GitHub 근거와 병합 상태 표시 | 본인 공개 PR만 저장 |
| 실패·계정 변경 | 성공 표시 없이 재시도·로그인 확인 안내 | 이전 기록 보존, 다른 계정에 저장하지 않음 |
| 운영자 확인 전달 선택 | 같은 이슈의 본인 전달 기록만 선택 | 명시한 활동에만 전달 ID 연결 |

`GET /api/contributions?expected_user_id=현재계정ID`는 본인의 기록, 운영자 확인 전달 목록과 집계를 반환한다.
`POST /api/contributions?action=start|cancel|resume|submit_pr|verify_pr`는 세션, 정식 Origin,
`expected_user_id`와 요청별 `event_id`를 검증한다. 전달 연결은 본인에게 실제 기록된 같은 이슈만 허용한다.
신규 기록은 공개 저장소의 실제 이슈인지 확인한다. 착수는 RepoBite의 개인 활동 기록이며 GitHub 담당자 지정은 아니다.

PR은 같은 저장소를 대상으로 하고 로그인한 GitHub 숫자 ID가 작성자인 공개 PR만 저장한다.
GitHub의 `merged_at`과 병합 상태를 확인한 고유 PR URL 수를 성공으로 집계한다.
이슈와 PR의 연결은 사용자 신고이며 해당 PR이 이슈를 닫았다고 추정하지 않는다.
동일 이벤트 재전송은 저장된 응답을 반환하므로 화면은 변경 뒤 GET으로 현재 상태를 재조회한다.
취소와 재개는 활동 상태만 바꾸며 검증된 PR 병합 근거를 삭제하지 않는다.
성공 횟수에 따른 등급 자동 확장은 제외했다.
