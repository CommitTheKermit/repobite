# 구독 즉시 수집과 화면 개편

확인일: 2026-10-23. 아래 정책은 시안 인계 문서의 미결정 초안을 대체한다.

## 확정 동작

- 구독 저장 성공 후 snapshot에 없는 저장소만 수집 요청을 저장한다. 같은 저장소의 요청과 이미 수집한 결과는 재사용한다.
- Vercel은 인증한 HTTPS 요청으로 Windows의 수집 전용 입구를 깨운다. 관리 웹의 로컬 Host/Origin 제한은 유지한다.
- 수집기는 요청이 있을 때만 한 저장소씩 실행한다. 유휴 큐 폴링과 별도 상시 수집 루프는 없다. HTTP 입구는 기존 웹 프로세스 안의 별도 loopback 리스너다.
- 실행 중에는 대기, GitHub 조회, 난이도 판정, 재시도 상태를 보여 준다. 진행률은 만들지 않는다. 총 3회 시도 후에도 완료하지 못했을 때만 실패를 표시한다. 재시도 간격은 첫 실패 후 5초, 두 번째 실패 후 10초다.
- 완료 알림은 자동으로 닫지 않고 `보기`를 누를 때까지 유지한다. 확인 기록을 계정별로 서버에 저장한 뒤 해당 저장소 상세를 연다. 같은 완료 알림은 새로고침·다시 로그인·다른 기기에서도 숨기며, 다른 사용자의 확인 여부에는 영향을 주지 않는다. 확인 저장에 실패하면 알림을 유지해 다시 시도할 수 있다. 반복 상태 조회 때 알림을 닫았다 열지 않으며 여러 알림은 화면 안에서 스크롤한다.
- 화면의 수집 상태 조회는 진행 중인 수집이 있을 때 5초, 없을 때 1분 간격이다. 숨은 탭에서는 조회하지 않고 다시 보일 때 즉시 조회한다. 온보딩에서 여러 저장소를 확정하면 저장을 모두 마친 뒤 피드와 수집 상태를 한 번만 다시 읽는다.
- 탐색의 `REPOSITORIES` 개수와 카드는 수집된 저장소와 수집 중인 저장소를 같은 기준으로 센다. 수집 전이거나 수집에 실패한 내 구독은 탐색에 올리지 않고 내 구독 화면과 온보딩 선택 목록에서만 보인다.
- 실패한 요청은 다음 정기 수집이 성공하면 완료로 갱신된다. 재시도 중 Windows가 중단되면 기록된 시도 횟수를 보존해 다음 요청 또는 웹 시작 시 복구한다.
- 정기 수집 목표는 한국시간 03:00, 09:00, 15:00, 21:00이다. 2026-10-23 확인 기준 운영 예약은 아직 03:00 하루 1회이며 6시간 트리거는 미적용이다(아래 "남은 예약 적용" 참고). 적용 전까지 실패한 즉시 수집은 최대 24시간 뒤 정기 수집에서 다시 시도된다. 대상은 기본 목록, 전체 개인 구독과 자동 발굴의 합집합이다. 이전 공용 등록은 포함하지 않는다. 기존 `repobite:repos` 키는 삭제하지 않으며 더 이상 읽거나 사용하지 않는다.
- 즉시 수집은 최근 7일, 저장소당 판정 최대 20건, 동시 판정 1개다. 정기 배치는 기존 최근 24시간, 실행당 100건, 저장소당 20건, 동시 판정 4개를 유지한다.
- 공개 피드는 구독 저장소 이름만 공개한다. 구독자 수, 사용자 식별자와 이메일은 공개하지 않는다. 내 구독도 구독된 레포 구역에 포함한다.
- 화면은 `web.html`, `repobite-app.mjs`, `repobite.css`, `repobite-dither.js`를 Vercel과 Windows에서 같이 쓴다. 이전 온보딩 URL은 새 hash 경로로 연결한다. 글꼴은 `assets/fonts/`에서 제공한다.
- 화면과 메일에는 Lv.1 쉬움, Lv.2 보통, Lv.3 어려움만 표시하고 이유와 준비 상태는 보여 주지 않는다. 판정 기준과 원본 저장 값은 바꾸지 않는다.

## 인증과 동시 실행

`REPOBITE_COLLECT_URL`은 Windows 수집 입구의 HTTPS `/collect` URL이다. Vercel에만 설정한다.
`REPOBITE_COLLECT_SECRET`은 32자 이상 임의 비밀이며 Vercel Production과 Windows 실행 계정의 사용자 환경변수에 같은 값으로 설정한다. 비밀을 Git·명령 인자·문서에 넣지 않는다.

요청 본문 시각과 nonce에 HMAC을 적용한다. 서버는 60초 시각 범위와 nonce 중복을 확인한다. GET과 다른 경로는 수집을 실행하지 않는다. 프런트엔드에 URL·인증 비밀을 제공하지 않는다.

`repobite:collect:jobs` 해시는 저장소별 단계·시도 횟수·갱신 시각을 보존한다. 공개 피드에 이 내부 해시를 내보내지 않으며 계정 상태 API는 본인 구독의 상태만 반환한다. 전송 실패는 구독 저장을 되돌리지 않고, 활성 요청 상태 조회 때 최대 15초에 한 번 실행 알림을 다시 전달한다.

`repobite:accounts:collection-seen:<계정 ID>` 해시는 저장소별 확인한 완료 식별자를 보존한다. 계정의 `collection` 조회는 완료 식별자와 확인 여부를 반환한다. `collection_seen` POST는 로그인·Origin·예상 계정·본인 구독·현재 완료 식별자를 검사하고 저장한다. 같은 확인은 반복 요청해도 안전하다. 새로운 수집 완료는 이전 확인과 구분하며, 이미 수집된 저장소의 일반 snapshot 갱신만으로 알림을 다시 만들지 않는다.

`repobite:collect:lock`은 정기 배치와 즉시 수집이 공유한다. 소유권은 120초 만료와 30초 갱신으로 유지하며 쓰기 직전 Lua 안에서도 확인한다. 잠금을 잃으면 snapshot을 저장하지 않는다. 정기 배치가 먼저 실행 중이면 즉시 수집은 실행권을 기다린다. 즉시 수집이 완료되면 해당 저장소 결과만 병합해 다른 저장소를 보존한다.

## 운영 반영

1. Windows 코드·추적 파일 변경과 예약 작업 계정을 확인한다. 같은 작업 브랜치의 정확한 커밋으로 배포한다.
2. Windows 사용자 환경변수에 수집 비밀을 설정한다. `scripts/run-web.ps1`은 기존 DB·GitHub·Vertex 인증과 함께 이를 프로세스에 주입한다.
3. 기존 `repobite-web` 작업을 재시작한다. 관리 웹, 상태 웹과 수집 전용 리스너를 각각 확인한다. 수집 전용 포트는 loopback 8768이다.
4. 기존 Funnel 설정을 보존하면서 수집 리스너만 HTTPS로 연결한다. 인증 없는 POST가 403인지 확인한다. 관리 웹을 외부에 노출하지 않는다.
5. Vercel Production에 URL과 인증 비밀을 설정하고 새 버전을 배포한다. 정식 주소의 deployment ID, HTML·CSS·JS·글꼴·`data.json`과 익명 계정 응답을 검사한다.
6. `scripts/update-batch-schedule.ps1`로 기존 작업의 트리거만 6시간 간격으로 변경한다. 기존 계정·실행 동작은 보존한다. Windows가 암호를 요구하면 서버 콘솔에서 암호를 안전하게 입력해 반영하고 등록 설정과 다음 실행 시각을 재확인한다.

## 운영 검증 기록 (2026-10-23)

### 완료 알림 확인 저장 후속

- Vercel 정식 주소는 `dpl_6EbqHQckz3HUQUnvQyU6YK993PtN`으로 갱신했고 Ready다. 일반 HTTPS의 HTML·서비스 모듈·CSS·검색 모듈·`data.json`은 로컬 파일과 일치하며 SSO 이동 없이 200이다. 익명 완료 확인 쓰기는 401이다.
- 계정·수집 단위 테스트 22개와 HTTP 실행 회귀, 기존 완료 상세·온보딩 브라우저 회귀, 로그인 조건 회귀가 통과했다. 정식 운영 화면에서도 모의 계정 API로 완료 알림 지속·반복 조회 중복과 깜박임 없음·확인 후 상세·새로고침 유지·계정 분리·실패 재시도·새 완료 구분을 확인했다. 실제 사용자 계정의 확인 기록은 검증 목적으로 변경하지 않았다.

### 최초 운영 반영

- 코드 브랜치는 `codex/redesign-subscribe-collect`다. Windows는 `24bfc2a`로 전환했고 추적 파일 변경은 없다. 기존 운영 브랜치는 보존했다.
- Vercel 정식 주소 `https://repobite.vercel.app`은 `dpl_F5vtP6Wq7MsPTJwDhY1QmY8haMic` 배포를 가리키며 Ready다. 이 배포의 서비스 코드는 `3551982`다. 이후 `24bfc2a`는 Windows 콘솔용 예약 갱신 스크립트만 바꾼다.
- 일반 HTTPS로 정식 주소의 HTML, CSS, JS 3개, 글꼴 2개, `data.json`을 받아 로컬 파일과 SHA-256 일치를 확인했다. SSO 리다이렉트 없이 200이며 익명 계정 API도 200이다. 공개 피드는 1,763건을 반환했고 화면은 현행 판정에 맞는 175건과 저장소 57곳을 표시했다.
- 운영 Chrome에서 1440/1000/390px 가로 넘침 없음, 상세 열기, 스크립트 오류와 CSP 차단 없음까지 확인했다. [데스크톱](verification/subscription-redesign-261023/desktop.png), [모바일](verification/subscription-redesign-261023/mobile.png), [상세](verification/subscription-redesign-261023/detail.png).
- 모의 계정 API를 사용하는 브라우저 검사에서 상세 구독 후 2단계 설정, 전체 4단계 설정, 수신 동의 기본 해제, 입력 DOM을 보존하는 검색, 재시도 중 실패 비노출과 최종 실패 표시가 통과했다. 실제 사용자의 OAuth 로그인과 설정 저장은 이번에 직접 실행하지 않았다.
- Windows `repobite-web` 재시작 후 Running과 관리 웹 HTTP 200, 새 모듈 연결 및 loopback 8768 리스너를 확인했다. 수집용 HTTPS 443 경로를 추가했고 기존 TCP 서비스 경로는 보존됐다. 관리 웹은 loopback 제한을 유지한다.
- 수집 입구는 loopback와 HTTPS 양쪽에서 인증 없음 403, 유효 서명 202, 동일 nonce 재전송 409를 반환했다. Mac 외부 HTTPS에서도 인증 없는 POST 403을 확인했다. Vercel Production과 Windows 사용자 환경에 수집 인증 설정을 주입했다. 실제 로그인 사용자에서 시작하는 Vercel 구독 요청의 전체 왕복은 별도 실사용 확인 대상이다.
- 실제 GitHub `neurosnap/zmx`를 임시 namespace의 요청 큐에 넣고 같은 수집기로 처리했다. 9건 수집, 9건 현행 판정, 첫 시도 done과 해당 저장소만 포함한 snapshot을 확인했다. 임시 DB 키는 finally에서 삭제했고 후보 파일도 임시 폴더에만 썼다. 운영 구독이나 snapshot을 검증용으로 바꾸지 않았다.
- Mac·Windows에서 계정, HTTP, 온보딩, 공용 배치, 메일, 최신성, 판정과 수집 회귀가 통과했다. Windows PowerShell 검사와 JavaScript 58건도 통과했다. `test_windows.ps1`에 나오는 PT0S는 테스트용 예약 작업의 결과이며 실제 운영 작업의 실행 제한 변경을 뜻하지 않는다.

### 남은 예약 적용

기존 Password 로그온 예약 작업의 트리거 변경이 `0x8007052e`로 거부됐다. 실제 운영 `repobite-batch`는 아직 03:00의 일일 트리거 1개이며, 확인 당시 다음 실행은 2026-10-24 03:00이다. 6시간 예약 적용 완료로 간주하지 않는다.

이 작업은 계정 암호와 함께 등록돼 있어 트리거만 바꿔도 같은 계정의 암호를 다시 입력해야 한다. 스크립트는 GUI 인증창 대신 가려진 콘솔 입력으로 암호를 받으므로 서버 콘솔 없이 Mac 터미널에서 `ssh -t`로 실행할 수 있다. 사용자가 터미널에 직접 입력하며 비밀값은 채팅, 명령 인자, 문서에 쓰지 않는다. `-BatchTime`은 첫 회차 시각이고 그 뒤 6시간 간격으로 하루 4회를 만든다. 시각을 다시 바꿀 때도 같은 명령에 새 `-BatchTime`을 넣어 실행한다.

```bash
ssh -t home-server "powershell -NoProfile -ExecutionPolicy Bypass -File <RepoBite 폴더>\scripts\update-batch-schedule.ps1 -BatchTime 03:00 -PromptForCredential"
```

실행 후 트리거 4개와 03/09/15/21시, 다음 실행 시각을 다시 확인해야 한다. 미래 예약 회차의 실제 실행은 등록이나 수동 수집 성공과 구분한다.

기존 `web.Application`의 상태·파일·프로세스 책임 혼합은 단일 책임 원칙 위반으로 남아 있다. 이번 수집은 별도 모듈에 두어 해당 클래스의 책임을 확대하지 않는다.
