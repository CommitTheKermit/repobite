# 구독 즉시 수집과 화면 개편

확인일: 2026-10-26. 아래 정책은 시안 인계 문서의 미결정 초안을 대체한다.

## 확정 동작

- 구독 저장 성공 후 snapshot에 없는 저장소만 수집 요청을 저장한다. 같은 저장소의 요청과 이미 수집한 결과는 재사용한다.
- Vercel은 인증한 HTTPS 요청으로 Windows의 수집 전용 입구를 깨운다. 관리 웹의 로컬 Host/Origin 제한은 유지한다.
- 수집기는 요청이 있을 때만 한 저장소씩 실행한다. 유휴 큐 폴링과 별도 상시 수집 루프는 없다. HTTP 입구는 기존 웹 프로세스 안의 별도 loopback 리스너다.
- 실행 중에는 대기, GitHub 조회, 난이도 판정, 재시도 상태를 보여 준다. 진행 토스트와 수집 중 카드에는 시안의 퍼센트 막대를 둔다(2026-10-26 사용자 결정). 서버는 단계만 알려 주므로 막대는 시간에 따라 99%까지만 다가가고, 100%는 `done`을 받은 뒤에만 잠깐 표시한 뒤 완료 알림으로 바꾼다. 실패는 100%를 표시하지 않는다. 새로고침하면 막대는 0%부터 다시 시작한다. 총 3회 시도 후에도 완료하지 못했을 때만 실패를 표시한다. 재시도 간격은 첫 실패 후 5초, 두 번째 실패 후 10초다.
- 2026-10-26 후속 결정: 새 구독 응답의 수집 접수 상태를 계정 재조회가 끝나기 전부터 표시한다. 진행 영역은 기존 완료 알림 위에 두고, 완료 목록은 화면 높이의 최대 40% 안에서 따로 스크롤한다. 새로 추가한 수집을 진행 영역 맨 위에 올리며, 재시도·조회 오류·일시적인 `idle` 응답으로 로딩을 없애지 않는다. 실제 `done` 또는 최종 `failed`에만 진행 표시를 끝낸다. 완료되면 해당 저장소의 알림을 완료 목록 맨 위에 둔다.
- 이미 수집돼 snapshot에만 있는 저장소(`attempt: 0`)는 새 수집 완료 알림을 만들지 않는다. 실제 수집 작업의 미확인 완료 알림과 계정별 확인 기록은 유지한다. 구독 이전에 시작된 늦은 상태 응답은 새 접수 상태를 덮어쓰지 않으며, 진행 중인 조회가 있으면 종료 후 새 구독을 포함해 한 번 더 읽는다.
- 완료 알림은 자동으로 닫지 않고 `보기`를 누를 때까지 유지한다. 확인 기록을 계정별로 서버에 저장한 뒤 해당 저장소 상세를 연다. 같은 완료 알림은 새로고침·다시 로그인·다른 기기에서도 숨기며, 다른 사용자의 확인 여부에는 영향을 주지 않는다. 확인 저장에 실패하면 알림을 유지해 다시 시도할 수 있다. 반복 상태 조회 때 알림을 닫았다 열지 않으며 여러 알림은 화면 안에서 스크롤한다.
- 화면의 수집 상태 조회는 진행 중인 수집이 있을 때 5초, 없을 때 1분 간격이다. 숨은 탭에서는 조회하지 않고 다시 보일 때 즉시 조회한다. 온보딩에서 여러 저장소를 확정하면 저장을 모두 마친 뒤 피드와 수집 상태를 한 번만 다시 읽는다.
- 탐색의 `REPOSITORIES` 개수와 카드는 수집된 저장소와 수집 중인 저장소를 같은 기준으로 센다. 수집 전이거나 수집에 실패한 내 구독은 탐색에 올리지 않고 내 구독 화면과 온보딩 선택 목록에서만 보인다.
- 실패한 요청은 다음 정기 수집이 성공하면 완료로 갱신된다. 재시도 중 Windows가 중단되면 기록된 시도 횟수를 보존해 다음 요청 또는 웹 시작 시 복구한다.
- 정기 수집 목표는 한국시간 03:00, 09:00, 15:00, 21:00이다. 2026-10-26 08:37에 운영 `repobite-batch`에 이 4개 트리거를 등록했다(아래 "예약 적용" 참고). 실패한 즉시 수집은 다음 정기 회차에서 다시 시도된다. 대상은 기본 목록, 전체 개인 구독과 자동 발굴의 합집합이다. 이전 공용 등록은 포함하지 않는다. 기존 `repobite:repos` 키는 삭제하지 않으며 더 이상 읽거나 사용하지 않는다.
- 즉시 수집은 최근 7일, 저장소당 판정 최대 20건, 동시 판정 1개다. 정기 배치는 기존 최근 24시간, 실행당 100건, 저장소당 20건, 동시 판정 4개를 유지한다.
- 공개 피드는 구독 저장소 이름만 공개한다. 구독자 수, 사용자 식별자와 이메일은 공개하지 않는다. 내 구독도 구독된 레포 구역에 포함한다.
- 저장소 설명과 카테고리는 아래 "저장소 자동 분류" 정책을 따른다. 즉시 수집과 정기 배치가 같은 분류기·캐시를 사용한다.
- 화면은 `web.html`, `repobite-app.mjs`, `repobite.css`, `repobite-dither.js`를 Vercel과 Windows에서 같이 쓴다. 이전 온보딩 URL은 새 hash 경로로 연결한다. 글꼴은 `assets/fonts/`에서 제공한다.
- 화면과 메일에는 Lv.1 쉬움, Lv.2 보통, Lv.3 어려움만 표시하고 이유와 준비 상태는 보여 주지 않는다. 판정 기준과 원본 저장 값은 바꾸지 않는다.

## 저장소 자동 분류 (2026-10-26)

사용자가 새 저장소를 구독하면 공개 상태를 확인한 GitHub 설명·토픽을 `repository_categories.py`에 전달한다. 기존 수동 카탈로그에 있는 저장소는 기존 설명·분류를 대소문자 구분 없이 유지한다. 목록 밖의 저장소는 기존 Vertex 모델로 한국어 설명과 기존 16개 분야 중 최대 3개를 정한다. 저장소 데이터의 지시는 따르지 않도록 프롬프트에서 구분하며, AI 응답의 필드·설명 길이·허용 분야·중복을 코드에서도 검사한다. 분류 근거가 없으면 분야를 강제하지 않는다.

성공한 분류는 `.radar-community/repository-categories.json`에 레포 이름 소문자 키로 저장하고 다음 즉시 수집·정기 배치에서 재사용한다. 이 파일은 기존 `.gitignore`의 수집 데이터 디렉터리 제외 규칙을 따른다. 캐시 버전 또는 모델이 바뀌면 재분류한다. 두 수집 경로의 기존 공용 잠금 안에서 원자적으로 파일을 교체한다. 공개 피드 조회 자체는 AI를 호출하지 않는다.

AI 오류·잘못된 응답·설명과 토픽 누락은 이슈 수집을 실패시키지 않는다. 그 회차에는 GitHub 설명과 빈 분야를 제공하고 실패를 캐시하지 않아 다음 수집에서 다시 시도한다. 캐시 파일이 없거나 손상된 경우에도 다시 분류하며, 캐시 쓰기 실패는 해당 회차의 성공한 분류 결과를 버리지 않는다. 오류 로그에는 외부 응답 원문을 넣지 않는다. Vertex에 보내는 JSON Schema는 [공식 지원 필드](https://docs.cloud.google.com/java/docs/reference/google-cloud-vertexai/latest/com.google.cloud.vertexai.api.GenerationConfigOrBuilder)에 맞추고 설명 길이·중복은 로컬 검증으로 제한한다.

공개 snapshot은 `repositories` 맵에 레포별 `description`, `categories`를 담고 이슈 항목에도 같은 값을 포함한다. 이슈가 0건이어도 레포 설명·분류를 표시할 수 있다. 화면은 레포별 맵을 우선하며 새 피드를 읽을 때 기존 분야를 지워 이전 분류가 누적되지 않게 한다. 기존 snapshot에 `repositories`가 없으면 이슈 항목의 값으로 표시한다. 기존 미분류 저장소는 다음 **성공한 정기 수집**에서 분류된다. 배포만으로 기존 snapshot을 즉시 다시 쓰지는 않는다.

분류와 카탈로그가 공개 이슈 변환에 섞여 있던 단일 책임 원칙 위반을 해소해 `public_feed.py`는 전달받은 메타데이터를 공개 필드로 변환한다. 이슈 난이도 판정과 저장소 분야 분류는 서로 독립적이다.

## 인증과 동시 실행

`REPOBITE_COLLECT_URL`은 Windows 수집 입구의 HTTPS `/collect` URL이다. Vercel에만 설정한다.
`REPOBITE_COLLECT_SECRET`은 32자 이상 임의 비밀이며 Vercel Production과 Windows 실행 계정의 사용자 환경변수에 같은 값으로 설정한다. 비밀을 Git·명령 인자·문서에 넣지 않는다.

요청 본문 시각과 nonce에 HMAC을 적용한다. 서버는 60초 시각 범위와 nonce 중복을 확인한다. GET과 다른 경로는 수집을 실행하지 않는다. 프런트엔드에 URL·인증 비밀을 제공하지 않는다.

`repobite:collect:jobs` 해시는 저장소별 단계·시도 횟수·갱신 시각을 보존한다. 공개 피드에 이 내부 해시를 내보내지 않으며 계정 상태 API는 본인 구독의 상태만 반환한다. 전송 실패는 구독 저장을 되돌리지 않고, 활성 요청 상태 조회 때 최대 15초에 한 번 실행 알림을 다시 전달한다.

`repobite:accounts:collection-seen:<계정 ID>` 해시는 저장소별 확인한 완료 식별자를 보존한다. 계정의 `collection` 조회는 완료 식별자와 확인 여부를 반환한다. 실제 수집 시도 없이 snapshot만 재사용한 `done`의 완료 식별자는 `null`이다. `collection_seen` POST는 로그인·Origin·예상 계정·본인 구독·현재 완료 식별자를 검사하고 저장한다. 같은 확인은 반복 요청해도 안전하다. 새로운 수집 완료는 이전 확인과 구분하며, 이미 수집된 저장소의 일반 snapshot 갱신만으로 알림을 다시 만들지 않는다.

`repobite:collect:lock`은 정기 배치와 즉시 수집이 공유한다. 소유권은 120초 만료와 30초 갱신으로 유지하며 쓰기 직전 Lua 안에서도 확인한다. 잠금을 잃으면 snapshot을 저장하지 않는다. 정기 배치가 먼저 실행 중이면 즉시 수집은 실행권을 기다린다. 즉시 수집이 완료되면 해당 저장소 결과만 병합해 다른 저장소를 보존한다.

## 운영 반영

1. Windows 코드·추적 파일 변경과 예약 작업 계정을 확인한다. 같은 작업 브랜치의 정확한 커밋으로 배포한다.
2. Windows 사용자 환경변수에 수집 비밀을 설정한다. `scripts/run-web.ps1`은 기존 DB·GitHub·Vertex 인증과 함께 이를 프로세스에 주입한다.
3. 기존 `repobite-web` 작업을 재시작한다. 관리 웹, 상태 웹과 수집 전용 리스너를 각각 확인한다. 수집 전용 포트는 loopback 8768이다.
4. 기존 Funnel 설정을 보존하면서 수집 리스너만 HTTPS로 연결한다. 인증 없는 POST가 403인지 확인한다. 관리 웹을 외부에 노출하지 않는다.
5. Vercel Production에 URL과 인증 비밀을 설정하고 새 버전을 배포한다. 정식 주소의 deployment ID, HTML·CSS·JS·글꼴·`data.json`과 익명 계정 응답을 검사한다.
6. `scripts/update-batch-schedule.ps1`로 기존 작업의 트리거만 6시간 간격으로 변경한다. 기존 계정·실행 동작은 보존한다. Windows가 암호를 요구하면 서버 콘솔에서 암호를 안전하게 입력해 반영하고 등록 설정과 다음 실행 시각을 재확인한다.
