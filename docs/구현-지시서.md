# RepoBite MVP 구현 지시서 (Codex 인계용)

> 이 문서는 Claude Code 세션에서 작성된 설계 결과를 Codex에 넘기기 위한 자족적 구현 지시서다.
> 구현자는 이 문서만으로 착수할 수 있다. 배경이 더 필요하면 아래 참고 문서를 읽는다.

**참고 문서**: `docs/기획서.md` (이 저장소 안에 있음)
(593줄, 20절 구성. 이 지시서의 모든 사양은 그 문서 17~20절에서 나왔다)

---

## 1. 배경

"오픈소스 기여를 망설이는 초보자에게, 지금 손댈 만한 이슈를 남보다 먼저 알려주는 서비스"를 기획 중이다.
핵심은 **라벨이 아니라 이슈 본문을 AI가 읽어 난이도를 판정**하는 것이다.

기획 단계에서 확인된 사실:

| 발견 | 근거 |
|---|---|
| `good first issue` 풀의 75.6%가 6개월 무활동 | GitHub Search API 집계 |
| `Proposed fix`가 본문에 있는 이슈 77,510건 중 GFI 라벨은 720건 (0.93%) | 동일 |
| 문자열 필터만으로는 정밀도 17% | 표본 30건 사람 판정 |
| 따라서 문자열 사전 필터를 두지 않고 AI가 전량을 읽는다 | 기획서 18절 |

**마지막 미결정**: 2축 등급 체계를 확정했으나(기획서 20절), 표본 30건은 단일축으로만 판정되어 있다.
실제로 초보자에게 보낼 **Lv.1 × ready 교집합이 몇 %인지 모른다.**

- 5% 미만이면 알림 물량이 부족해 서비스가 심심해진다
- 40%를 넘으면 사실상 걸러지는 게 없다

## 2. 목표

1. **Lv.1 × ready 비율을 측정한다** (이게 주 산출물)
2. 파이프라인 1·3단계 구현체를 확보한다 (이후 재사용)
3. 판정기 신뢰도를 측정한다 (7절의 사람 판정 30건 대비 일치율)

## 3. 범위

**포함**: 수집기 / 제외 필터 / 판정기 / 리포트
**제외**: 알림 발송, 웹 UI, DB, 스케줄러, 사용자 계정, 개인화

알림 채널은 기획 단계에서 아직 미결정이라 이번 범위 밖이다.

## 4. 위치와 작업 규칙

**위치**: `~/Desktop/dev/myDev/repobite` (이미 생성됨. `docs/`만 들어 있는 상태)

- 아직 git 저장소가 아니다. `git init` 후 `docs/` 포함해 초기 커밋부터 시작
- 커밋 메시지는 Conventional Commits (`type(scope): 요약`), 요약과 본문은 한글
- 단계별로 의미 단위 커밋
- em dash(-) 사용 금지, 일반 hyphen(-) 사용

## 5. 기술 선택

| 항목 | 선택 | 이유 |
|---|---|---|
| 수집 | `gh api` subprocess | 이미 인증돼 있음. 토큰을 직접 다룰 필요 없음 |
| 판정 | `codex exec` subprocess | 구독 사용. API 키 불필요 |
| 언어 | Python 3.14 표준 라이브러리만 | pip install 없음, venv 없음 |

의존성을 추가하지 않는다. `requests`, `anthropic`, `openai` 모두 불필요하다.

확인된 환경: Python 3.14.5 / gh 인증됨(CommitTheKermit) / codex-cli 0.153.4 ChatGPT 로그인됨


## 7. 사양

### 7.1 `radar.py collect`

**Search API를 쓰지 않는다.** 이유는 실측된 레이트 리밋 차이다.

| API | 한도 |
|---|---|
| Search API | 분당 30회 (+ 별도 secondary rate limit) |
| Core API | 시간당 5,000회 |

또한 이슈 검색에서 `stars:` 한정자는 **동작하지 않는다** (임계값을 올려도 단조 감소하지 않음을 확인).
따라서 레포 목록을 직접 보유하고 레포별로 순회한다.

```
gh api "repos/{repo}/issues?state=open&since={ts}&per_page=100" --paginate
```

- `repos.txt`의 레포를 순회
- `--since`는 `7d` 같은 상대 표기를 받아 ISO8601로 변환
- 출력: `issues.jsonl` (repo, number, title, body, url, created_at, labels, user)

> 주의: Core API의 `since`는 **갱신(updated) 기준**이지 생성 기준이 아니다.

### 7.2 제외 필터

| 조건 | 판별 |
|---|---|
| PR | 응답에 `pull_request` 필드 존재 |
| 담당자 있음 | `assignee`가 non-null |
| 봇 작성 | `user.type == "Bot"` 또는 login이 `[bot]`으로 끝남 |

봇 필터가 필요한 실제 사례: `alebertolli/idos#79`는 CI 실패를 봇이 자동 생성한 이슈인데
템플릿 문구에 "proposed fix"가 들어 있어 문자열 필터를 통과했다. 로그조차 404로 못 가져온 상태였다.

> **미구현으로 남기는 것**: 이미 PR이 걸린 이슈 제외.
> timeline API 호출이 이슈당 1회 추가로 필요해 MVP 범위에서 뺀다.

### 7.3 `radar.py grade`

이슈 1건당 `codex exec` 1회 호출.

```
codex exec --output-schema schema.json -o <tmp> --ephemeral \
           -s read-only --skip-git-repo-check "<프롬프트>"
```

`concurrent.futures.ThreadPoolExecutor(4)`로 병렬 처리. 표준 라이브러리라 의존성이 늘지 않는다.
출력: `grades.jsonl`

**`schema.json`**:

```json
{
  "type": "object",
  "properties": {
    "difficulty":     {"type": "integer", "enum": [1, 2, 3]},
    "readiness":      {"type": "string", "enum": ["ready", "needs_info", "undecided"]},
    "reason":         {"type": "string"},
    "exclude":        {"type": "boolean"},
    "exclude_reason": {"type": "string"}
  },
  "required": ["difficulty", "readiness", "reason", "exclude"],
  "additionalProperties": false
}
```

**`reason` 필드는 필수다.** 기획서 20절에서 "초보자 신뢰 확보"를 판정 이유 제시로 풀기로 했다.
등급만 보여주면 초보자는 안 믿지만 "수정 위치가 본문에 있고 3줄 수정"은 믿는다.
따라서 판정 시점에 알림에 실을 근거 문구를 같이 받아둔다.

### 7.4 판정 기준 (프롬프트에 그대로 실을 것)

두 축은 독립이다. 하나로 뭉치지 말 것.

**난이도 `difficulty` (1이 가장 쉬움)**

| 신호 | 1 | 3 |
|---|---|---|
| 도메인 지식 | 코드만 보면 됨 | 보안·인프라·분산 등 배경 필요 |
| 변경 범위 | 한 파일 수 줄 | 여러 계층 동시 수정 |
| 검증 | 로컬 재현 가능 | 특수 환경·타이밍 의존 |

**준비도 `readiness`**

| 신호 | `ready` | `undecided` |
|---|---|---|
| 수정 위치 | 파일·함수·라인 명시 | 어디를 고칠지 미상 |
| 수정 내용 | diff 수준 | 방향만 (`direction`) |
| 재현 절차 | 있음 | 없음 |
| 결정 상태 | 무엇을 할지 확정 | 설계 판단이 남음 |

`needs_info`는 그 중간(일부는 있으나 착수 전 보완이 필요).

**두 축을 왜 나누는가**: 표본에서 부적합 16건 중 8건이 "어려워서"가 아니라
**"아직 안 정해져서"** 부적합이었다. 한 축으로 뭉개면 진짜 어려운 이슈(나중에 경력자용 자산)와
정보가 없는 쓰레기가 같은 칸에 들어간다.

**판정 예시** (프롬프트에 few-shot으로 넣으면 좋음):

- `massimoaria/bibliometrix#666` → difficulty 1, readiness ready
  (본문에 diff가 그대로 있고 `R/csvOA2df.R:397` 한 줄 수정)
- `simonives/redwrench#43` → difficulty 2, readiness undecided
  (`Proposed fix direction`만 있고 정책 판단이 남음)

`exclude`는 원인 미상이거나 가설이 반증된 이슈처럼 수집 단계에서 못 거른 것을 표시한다.

### 7.5 `radar.py report`

| 산출물 | 설명 |
|---|---|
| **난이도 × 준비도 교차표** | 핵심 |
| **Lv.1 × ready 비율** | 이게 목표 1의 답 |
| 레포별 분포 | 아래 집중도 문제 확인용 |
| 사람 판정 대비 일치율 | `fixtures/sample30.json`이 있을 때만 |

> **레포 집중도**: 이전 표본에서 `simonives/redwrench` 한 곳이 30건 중 11건(37%)을 차지했고,
> 상위 3개 레포가 57%였다. 실측 레포별 주간 이슈량에서도 vscode 하나가 9개 레포 합계의 45%였다.
> 레포별 상한은 알림 단계 기능이라 이번 범위 밖이지만, **리포트에서는 반드시 보이게 한다.**

## 10. 실행 순서

1. `repos.txt`에 레포 10~20개 (아래 실측 목록 참고)

## 11. 열린 항목

- **비용 모델은 검증되지 않는다.** codex 구독이라 API 과금이 아니다.
  기획서의 월 $10~$50 추정은 그대로 미검증으로 남는다
- 이미 PR이 걸린 이슈 제외 (timeline API 필요)
- 레포별 상한 (알림 단계 기능)
- 번역 공백 발굴 축 (기획서 9절). 이슈가 아니라 레포 구조를 보는 별도 경로라 이번 범위 밖
