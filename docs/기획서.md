## 2. 문제 정의

- 사람들은 오픈소스 기여를 어렵다고 생각한다
- 그러나 실제로는 아주 쉽게 고칠 수 있는 이슈가 분명히 존재한다
- 특히 AI가 웬만한 개발자보다 나은 지금, 난이도는 더 내려갔다
- 따라서 진짜 장벽은 실력이 아니라 **"내가 손댈 만한 이슈를 못 찾는 것"**

## 3. 제안 서비스

"쉬운 기여"가 가능한 이슈를 찾아 알려주는 알림 서비스.
핵심: **남이 낚아채가기 전에 먼저 알려준다** (선점 = 시의성이 곧 가치)

**수집 대상 3종**
1. 유명한 오픈소스 프로젝트
2. 지금 핫한 오픈소스 프로젝트
3. 내가 등록한 오픈소스 프로젝트

**동작**: 스케줄러가 주기적으로 이슈를 긁어 알림 발송

## 5. 알려진 불만 - "good first issue 라벨은 못 믿는다"

[The "good first issue" myth (DEV)](https://dev.to/dzhavat/the-good-first-issue-myth-204c) 직접 확인:

- 인기 프로젝트는 라벨을 거의 안 씀 (Angular: 열린 이슈 2,685건 중 라벨 1건)
- 수년 전 이슈가 그대로 남아 있음 (2018년 것 다수)
- 이미 PR이 걸려 있거나 `good first issue (taken)` 상태
- Bootstrap, jQuery 등은 이 라벨 체계를 아예 안 씀

관련: [Good First Issues: beginner beware (Quira)](https://medium.com/quira/good-first-issues-beginner-beware-4dff2c9c8ea1),
[Stop browsing "good first issues" (Quansight)](https://labs.quansight.org/blog/dont-start-with-good-first-issues) (미확인, HTTP 429)

# 판정 로직

아오의 "쉬웠던 이유" 2가지를 실제 원본과 대조해 탐지 가능한 신호로 변환.

## 9. 신호 1 - "AI에 맡기고 검수만 하면 되는 작업"

근거: PR #2177 (문서 번역). 기여 가이드라인에도 명시되어 있음.

`CONTRIBUTING.md:352`:
> `- Translating documentation (if you speak multiple languages)`

즉 프로젝트가 **번역을 공식 입문 경로로 안내**하고 있었음.

**탐지 신호**
- CONTRIBUTING이 번역/문서 기여를 입문 경로로 명시하는가
- 다국어 문서 구조가 있는가 (`README.ko.md`, `docs/*.ko.md`)
- 영어 원문은 있는데 특정 언어 번역본이 없는 문서가 있는가
- 이슈가 `documentation` 계열인가

> **이 축은 이슈를 긁는 것과 별개.** 레포 구조만 봐도 기회를 만들어낼 수 있다.
> "이 프로젝트는 한국어 번역본이 없다" 자체가 알림 소재. 경쟁 서비스에 없는 축.

## 10. 신호 2 - "이슈만으로 컨텍스트가 충분함"

근거: 이슈 #2198. 실제 본문 섹션 구조:

```
## Problem            (무엇이 왜 깨지는가 + 원인 함수 _read_json() 지목)
## Expected behavior  (수용 기준 3개)
## Reproduction       (재현 절차)
## Proposed fix       (UnicodeDecodeError를 _read_json() 경계에서 잡고 회귀 테스트 추가)
```

★ **결정적 관찰: 이 이슈에는 라벨이 하나도 없었다 (`labels: []`)**

기존 라벨 기반 서비스 6개는 이 이슈를 **구조적으로 영원히 못 찾는다.**
아오가 가장 쉽다고 느낀 바로 그 이슈를. (8절의 77,510 vs 720이 이게 우연이 아님을 뒷받침)

**탐지 신호 (본문 파싱)**
- `Proposed fix` / `Suggested fix` / 수정 제안 섹션 존재
- `Reproduction` / `Steps to reproduce` 존재
- `Expected behavior` / 수용 기준 존재
- 본문에 구체적 심볼 지목 (함수명 / 파일명 / 에러 타입)
- 이미 걸린 PR이 없을 것

# 파이프라인과 비용

## 11. 3단계 구조 - 판정은 AI가, 그 앞은 깔때기

**핵심: 실제 난이도 판정은 AI(LLM)가 한다.** 문자열 규칙은 판정자가 아니라 그 앞에 붙는 비용 절감 장치.

### 유입량 (GitHub Search API, 2026-09-09 집계)

| 구간 | 주당 건수 |
|---|---|
| GitHub 신규 이슈 전체 | **686,799** |
| 그중 본문에 `Steps to reproduce` 포함 | 26,341 |
| 그중 본문에 `Proposed fix` 포함 | 5,740 |

### 단계별 역할

| 단계 | 하는 일 | 남는 양 | 비용 |
|---|---|---|---|
| 1. 수집 범위 | 레포 목록 한정(유명/핫한/등록한) + 신선도 필터 | 68.7만 → 수만 | 무료 (GitHub API) |
| 2. 값싼 선별 | 구조 신호로 후보 축소 | 수만 → 수천 | 무료 |
| **3. AI 판독** | **실제 난이도, 완주 가능성, 한 줄 요약** | 수천 | 아래 표 참조 |

### 왜 깔때기가 필요한가 - 비용

Claude Haiku 4.5 기준 ($1 / $5 per MTok), Batch API 50% 할인 적용.
이슈당 입력 1,000토큰 / 출력 100토큰 **가정** (토큰량은 추정치).

| 대상 | 주당 | 월 환산 (Batch 적용) |
|---|---|---|
| 전량 686,799건에 AI 태우기 | 약 $1,030 | **약 $2,200** |
| 26,341건으로 좁힌 뒤 | 약 $40 | **약 $85** |

약 26배 차이. 개인 프로젝트에서 월 $2,200은 불가, 월 $85는 가능.
**깔때기의 존재 이유는 이것 하나뿐이고, 판정 품질과는 무관하다.**

### 2단계 설계 시 함정 ★

2단계를 문자열 매칭으로 좁게 짜면 **라벨 기반과 똑같은 실수를 반복한다.**
`Proposed fix`라는 표현을 안 쓰고 같은 내용을 적은 이슈를 놓치기 때문.
라벨이 없어서 못 찾던 것을, 이번엔 문자열이 없어서 못 찾는 구조.

→ 2단계는 판정이 아니라 **넓게 거르는 그물**이어야 함.
좁히면 싸지만 놓치고, 넓히면 안 놓치지만 비싸다.
위 표의 **26,341 대 5,740**이 그 선택지이고, 어디서 자를지가 실제 설계 결정.

## 12. GitHub Search API 제약 - `stars:`는 이슈 검색에서 동작하지 않음

스케줄러 설계에 직접 영향. 검증 결과:

| 쿼리 조건 (신규 이슈 7일) | 결과 |
|---|---|
| `stars:>1` | 29,846 |
| `stars:>1000` | 124 |
| `stars:>100000` | 1 |
| `stars:>99999999` | **2** |

존재할 수 없는 임계값이 더 큰 값을 반환. 진짜 숫자 필터라면 단조 감소해야 하고 마지막은 0이어야 함.
즉 **이슈 검색에서 `stars:`는 필터가 아니라 텍스트로 취급된다.**

반면 `repo:` 한정자는 정상 동작 (`repo:microsoft/vscode` → 주당 400건).

**함의**
- "스타 많은 레포의 이슈"를 쿼리 한 방으로 못 가져옴
- **레포 목록을 서비스가 직접 보유해야 함**
- 아오의 수집 대상 3종(유명/핫한/등록한)이 곧 그 목록. 기획과 일치
- 파이프라인 1단계는 단일 쿼리가 아니라 **레포별로 나눠 도는 구조**가 됨

> 미확인: `repo:facebook/react`는 HTTP 422를 반환. 일시적 오류인지 권한 문제인지 미확인.


# 결론

## 13. 차별점 4종

| 축 | 경쟁 서비스 | 우리 | 근거 |
|---|---|---|---|
| **이슈 발굴** | `good first issue` 라벨 필터 | **본문 파싱** (라벨 없어도 잡음) | #2198은 무라벨 / 77,510 vs 720 |
| **신선도** | 6개월 무활동 75% 그대로 노출 | 신선도 필터로 주당 3,700건만 | 6절 집계 |
| **레포 선택** | 직접 구독(IssueWatch) 또는 정적 큐레이션 | 유명/핫한 프로젝트 자동 발굴 | 초보자는 뭘 구독할지 모름 |
| **기회 생성** | 이슈만 봄 | **번역 공백 발굴** (이슈가 없어도 기회 생성) | CONTRIBUTING:352 / PR #2177 |

가장 강한 축은 **레포 발굴**과 **본문 파싱**.
구독형(IssueWatch)은 이미 뭘 구독할지 아는 사람용이고, 우리 타겟은 그걸 모르는 사람이다.

## 20. 등급 체계 (2026-09-10 확정)

### 원칙 - 버리지 않는다

**"쉽지 않으면 버린다"가 아니라 "전부 등급을 매겨 보관한다."**
3단계에서 어차피 전량을 읽으므로 출력이 이진값에서 등급으로 바뀔 뿐, **비용은 동일**하다.

```
판정   1단계 통과분 전량에 등급 부여   ← 아무것도 안 버림
저장   전부 보관 (등급 + 판정 이유)
알림   등급별로 다르게 (하위 등급은 안 보내되 조회는 가능)
```

> "버리지 않는다"가 "전부 알림 보낸다"는 아니다. **저장과 알림을 분리**한다.

### 2축 구조

| 축 | 값 | 무엇을 재나 |
|---|---|---|
| **난이도** | **Lv.1 / Lv.2 / Lv.3** (1이 쉬움) | 코드를 고치는 난이도 |
| **준비도** | **바로 착수 / 보완 필요 / 미정** | 본문만으로 뭘 할지 아는가 |

**왜 2축인가**: 17절 부적합 16건 중 8건이 "어려움"이 아니라 "아직 안 정해짐"이었다.
한 축으로 뭉개면 **진짜 어려운 이슈(자산)와 봇 쓰레기(노이즈)가 같은 칸**에 들어가
7절에서 확인한 "어려운 이슈는 라벨이 없어 아무도 못 찾는다"는 기회를 못 쓰게 된다.

아오의 #2198이 쉬웠던 이유도 이 구조로 정확히 설명된다.
난이도가 낮아서가 아니라 **준비도가 최상**이었다 (Problem / Expected behavior / Reproduction / Proposed fix 완비).
반대로 redwrench 8건은 난이도는 중간이어도 준비도가 미정.

### 축별 판정 신호

**난이도 (Lv.1 → Lv.3)**

| 신호 | Lv.1 | Lv.3 |
|---|---|---|
| 도메인 지식 | 코드만 보면 됨 | 보안·인프라·분산 등 배경 필요 |
| 변경 범위 | 한 파일 수 줄 | 여러 계층 동시 수정 |
| 검증 | 로컬 재현 가능 | 특수 환경·타이밍 의존 |

**준비도 (바로 착수 → 미정)**

| 신호 | 바로 착수 | 미정 |
|---|---|---|
| 수정 위치 | 파일·함수·라인 명시 | 어디를 고칠지 미상 |
| 수정 내용 | diff 수준 | 방향만 (`direction`) |
| 재현 절차 | 있음 | 없음 |
| 결정 상태 | 무엇을 할지 확정 | 설계 판단이 남음 |

### 제외 필터 (등급이 아니라 배제)

- 봇 생성 이슈 (17절 idos#79 사례)
- 원인 미상 / 가설이 반증된 이슈
- 이미 PR이 걸린 이슈
- 담당자 배정된 이슈

### 초보자 알림 대상

**Lv.1 × 바로 착수** 교집합. 알림 표기 예:

```
[Lv.1 · 바로 착수]
bibliometrix#666
R/csvOA2df.R:397 한 줄 수정. 본문에 diff 있음
```

### 이 구조로 해결되는 것

| 기존 미결정 | 해결 방식 |
|---|---|
| 5번 개인화 기준 | **난이도가 개인화 축이 됨.** 성공 누적 시 Lv.2로 상향하는 성장 경로 |
| 7번 초보자 신뢰 확보 | **판정 이유가 그대로 근거가 됨.** 등급만으론 못 믿지만 "수정 위치가 본문에 있고 3줄"은 믿는다 |
| 7절 경력자 확장 보류 | **우리가 매긴 등급이 곧 없는 라벨.** Lv.3 × 바로 착수가 경력자용 자산 |

### 남은 것

- 등급 경계 캘리브레이션 - 표본에서 Lv.1 비율이 실제로 알림 보낼 만큼 나오는지
  (17절 단일축 기준으로는 적합 17%. 2축 재판정은 미실시, **미확인**)
- 판정 이유를 몇 자로 쓸지 (알림에 들어갈 분량)
