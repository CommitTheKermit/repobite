# 저장소 자동 발굴

확인일: 2026-10-21.

사용자 확정 정책은 이번 주 GitHub Trending 최대 15개와 누적 별 수 상위 15개다.
목표는 총 30개지만 적격 Trending이 1-14개이면 확보한 Trending과 유명 저장소 15개를 사용한다.
실제 확보 수만 표시하며 부족 라벨은 화면에 표시하지 않는다. 원본 건수와 부족분은 내부 JSON에 보존한다.
`repository_discovery.py`는 기존 `repos.txt`, 공용 등록 목록, 개인 구독 목록을 변경하지 않는 후보 제안 모듈이다.
공유 배치와 문서 라우팅의 실제 연결은 호출하는 쪽에서 담당한다.

## 실행

```sh
python3.14 repository_discovery.py --source github-trending --limit 30 --period weekly --allow-partial-trending
```

`--source`와 양의 짝수 `--limit`는 필수다. GitHub Trending 모드는 `--period daily|weekly|monthly`를
명시해야 하며, 운영 정책에서는 `weekly`를 사용한다. 출력 기본값은 `repository-discovery.jsonl`이고
`--output`으로 바꿀 수 있다. 이 파일은 JSON 객체 한 개다.
`--allow-partial-trending`을 명시해야 일부 Trending을 허용한다. 생략하면 15:15를 모두 확보해야 성공한다.

## 원천과 선정

### GitHub Trending

원천은 [주간 Trending](https://github.com/trending?since=weekly)의 공개 HTML이다.
사용 가능한 GitHub 커넥터에 Trending 조회가 없어 HTTP로 읽는다. 저장소별 제목 링크와 페이지 순위,
`stars this week` 값을 파싱한다. 이 수치는 자체 관측의 7일 별 순증가와 구분한다.
GitHub가 표시한 주간 기준이며 정확한 시작·종료 시각을 새로 추정하지 않는다.

HTML 원천 URL, 선택 기간, 조회 시각, 바이트 수와 SHA-256을 출력한다.
HTTP 200, HTML 형식, 요청한 최종 URL, Content-Length가 있으면 실제 수신 길이,
문서 끝과 결과 article 구조, 제목·링크 일치, 기간별 별 수를 확인한다.
로그인 화면, 부분 응답, 구조 변경, 중복 제목, 파싱 실패를 빈 결과로 처리하지 않는다.

순위대로 저장소 메타데이터를 확인하며 비공개·보관됨·사용 중지·이슈 기능 꺼짐은 제외하고 다음 순위를 확인한다.
GitHub ID로 중복을 구분한다. 적격 저장소가 15개보다 적어도 일부 허용 옵션을 지정하면 확보한 수를 사용한다.
빈 원천이나 적격 저장소 0개는 실패하며 다른 기간이나 유명 저장소로 빈자리를 대체하지 않는다.

### 누적 별 수

[GitHub 저장소 검색 API](https://docs.github.com/en/rest/search/search#search-repositories)의
`sort=stars&order=desc`와 별 수 하한을 사용한다. 시작 쿼리는 다음과 같다.

```text
stars:>=100000 is:public archived:false fork:true
```

100,000은 사용자에게 제안할 저장소의 고정 자격 기준이 아니라 검색 응답을 좁히기 위한 시작 하한이다.
`fork:true`로 포크도 검색 모집단에 포함한다. 한 구간의 검색 결과를 전부 읽고 다음을 확인한다.

- 모든 페이지의 `incomplete_results=false`
- 페이지 사이에 같은 `total_count` 유지
- 누락 없이 `returned_count == total_count`
- 저장소 ID 중복 없음, 별 수 내림차순과 검색 하한 유지

검색 API의 1,000건 반환 한도를 넘는 구간, 불완전한 응답, 페이지 누락이나 결과 변동은 실패한다.
불완전한 결과를 허용하거나 임의의 인기 저장소 목록으로 대체하지 않는다.

검색 결과 전체를 [저장소 API](https://docs.github.com/en/rest/repos/repos#get-a-repository)로 재확인한다.
검색과 현재 메타데이터의 ID가 같아야 하며 공개·미보관·활성·이슈 활성화 조건을 모두 충족해야 한다.
Trending에서 먼저 선택한 ID를 제외하고 누적 별 수 내림차순, 동점이면 저장소 이름 순으로 15개를 고른다.
최종 15번째 저장소의 현재 별 수가 검색 하한 이상인 경우에만 하한 아래 검색을 생략한다.
부족하면 하한을 절반으로 낮춰 전체 검색을 다시 수행한다. 가장 낮은 구간까지 부족하면 실패한다.

출력에는 사용한 모든 검색 쿼리·하한·URL·전체 및 반환 건수, 개별 메타데이터 원천과 관측 시각을 남긴다.
이 순위는 GitHub 검색 인덱스와 이후 API 관측을 근거로 하며, GitHub 전체의 동일한 한 시점에 대한
원자적 스냅샷은 아니다. 검색 색인과 현재 메타데이터의 차이를 숨기지 않는다.

## 출력과 배치 연결 계약

운영 호출은 `run_github_trending(limit=30, period="weekly", allow_partial_trend=True, output_path=...)`이다.
`allow_partial_trend`의 기본값은 `False`다. 성공 시 아래 계약의 객체를 반환하고 저장한다.

| 필드 | 의미 |
|---|---|
| `version` | 산출물 형식 버전 `1` |
| `method` | `github_trending_and_cumulative_stars` |
| `requested_total` | `30` |
| `actual_total` | 실제 선정 수, 일부 허용 시 `16-30` |
| `quota` | `trend: 15`, `famous: 15` |
| `trend` | `items` 1-15개, `shortfall`은 `15 - len(items)`, 충족 시 `status: complete`, 일부 확보 시 `partial` |
| `famous` | `status: complete`, `shortfall: 0`, `items` 15개 |
| `repos` | 확보한 Trending 다음 유명 15개인 고유 저장소 이름 배열, 길이는 `actual_total` |
| `source` | Trending 원천, 유명 검색 전체성 근거, 제외 상태, 순위 관측의 한계 |
| `generated_at` | 결과 생성 UTC 시각 |

배치는 필드 계약, 개수, 이름과 중복을 검증한 뒤 기존 기본 목록·공용 등록·개인 구독에 `repos`를
대소문자를 무시하는 합집합으로 더한다. 제안에서 빠진 저장소라는 이유로 기존 수집 대상을 제거하지 않는다.
이 모듈 자체는 운영 수집 목록을 저장하거나 스케줄을 등록하지 않는다.

`source.trending.rows`는 HTML 원본 순위 개수이며 선정 개수와 다를 수 있다.
`source.excluded`는 확인한 저장소별 제외 사유를 같은 이름 기준으로 한 번씩 집계한다.
`shortfall`과 `partial`은 내부 근거다. 화면과 CLI 성공 문구에는 확보한 후보 개수만 표시하고 총 30개를 확보했다고 주장하지 않는다.

모든 HTTP·GitHub 조회, 파싱, 유명 15개와 선택한 Trending 정책 검증이 끝난 뒤 임시 파일을 교체해 출력한다.
원천 조회·파싱·적격 Trending 0개·유명 후보 부족·API 오류 시 기존 후보 출력을 유지하고 CLI는 종료 코드 1을 반환한다.
일부 허용 옵션이 없으면 Trending 부족도 실패한다.
호출 배치는 이 실패를 전파하여 이전 공개 스냅샷을 유지해야 한다.

## 자체 관측 보조 모드

이전의 자체 7일 별 순증가 모드는 별도로 보존한다.

```sh
python3.14 repository_discovery.py --source own-history --limit 30 --tolerance-hours 1
```

위 명령의 허용 오차 1시간은 실행 예시이며 운영의 자동 기본값이 아니다.
`--tolerance-hours`는 필수이며 0 이상 168 미만을 지정한다. 같은 GitHub ID의 관측 중
7일 전 목표와 명시 오차 안에서 가장 가까운 기록을 비교한다. 기준 관측과 실제 시간차, 별 순증가를 남긴다.
기록이 없으면 `unmeasured`와 부족분을 출력하고 유명 몫으로 대체하지 않는다.
이 보조 모드 결과를 GitHub Trending 정책의 30개 결과로 소비하지 않는다.

별 관측 기록은 `.repository-stars.jsonl`에 누적하며 보관 기간 자동 정리는 구현하지 않았다.

## 검증 범위

`python3.14 test_repository_discovery.py`는 외부 호출을 대체하여 HTML 구조 변경, 기간 불일치,
부분 응답, 다음 순위 충원, 원천 중복 제거, 검색 완전성, 하한 확장, 후보 부족과 오류 시 출력 보존을 확인한다.
일부 Trending 허용은 명시 옵션이 있어야 하며, 14+15개 성공과 원천 오류·유명 후보 부족 시 보존을 추가로 확인한다.
실제 외부 원천의 최신 순위와 운영 배치 완료는 별도의 실행 근거로 확인한다.


### 실제 원천 점검 (2026-10-21)

주간 HTML에서 15개 article과 순위를 파싱했다. 원천 15개를 개별 API로 확인한 결과 적격 14개,
이슈 기능 꺼짐 1개였다. [mksglu/context-mode의 메타데이터](https://api.github.com/repos/mksglu/context-mode)는
`id=1164477708`, `has_issues=false`로 확인했다. 처음의 엄격 모드 실제 실행은 15:15 결과를 만들지 못하고
유명 저장소 검색 전에 종료 코드 1로 종료했다. 이후 사용자가 적격 Trending 일부 사용을 확정했다.

누적 별 검색 원천은 `stars:>=100000 is:public archived:false`에서 `incomplete_results=false`,
`total_count=133`을 확인했고 포크 포함 `fork:true` 쿼리도 같은 완전성과 건수를 확인했다.
HTML·API는 변동하므로 이 숫자는 해당 확인일의 스냅샷이다.

일부 허용 실제 실행은 `2026-10-21T02:14:49Z`에 주간 HTML을 읽고 `02:15:12Z`에 결과를 생성했다.
원본 순위 15개 중 적격 Trending 14개와 유명 15개, 고유 저장소 29개를 저장하고 종료 코드 0을 반환했다.
`requested_total=30`, `actual_total=29`, `trend.status=partial`, `trend.shortfall=1`이며
유명 몫은 `status=complete`, `shortfall=0`이다. 유명 검색은 하한 100,000의 전체 133건을
2페이지로 읽고 `incomplete_results=false`를 확인했다. 선정한 마지막 유명 저장소의 현재 별 수는
251,592개로 검색 하한보다 높았다. 전체 확인 저장소의 제외 사유는 이슈 기능 꺼짐 14개였으며,
그중 Trending 원천에서 제외한 저장소는 앞서 확인한 1개다.

이 실행은 발굴 모듈의 원천 조회와 후보 산출 검증이다. 운영 배치 통합이나 공개 서비스 반영 완료를 뜻하지 않는다.
