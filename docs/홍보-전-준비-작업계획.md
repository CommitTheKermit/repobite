# RepoBite 홍보 전 필수 항목 작업 계획

이 문서는 Codex에 그대로 전달할 작업 지시서다. 이 문서와 저장소 루트의 `AGENTS.md`, `README.md`만으로 진행한다.
목표는 공개 홍보 직전, 처음 온 사람이 서비스를 이해하고 운영자가 반응을 측정할 수 있는 상태를 만드는 것이다.

## 작업 규칙

- 새 브랜치 `feat/launch-readiness`에서 작업한다. 아래 작업 단위마다 Conventional Commits 형식의 한글 커밋을 남긴다.
- 비밀값, 실제 DB 주소, 서명 트레일러는 커밋하지 않는다.
- 새 Python 패키지와 npm 패키지를 추가하지 않는다. 기존처럼 Python 표준 라이브러리와 Node 표준 모듈만 쓴다.
- `web.html`은 현재처럼 한 파일에 둔다. 테스트(`test_web_ui.mjs`)와 Vercel 배포 허용 목록(`.vercelignore`)이 이 구조를 전제로 한다.
- 서버 측 새 로직은 API 핸들러(`api/*.py`, 요청 검증·응답)와 저장 모듈(`metrics.py`, Redis 접근·집계)로 나눈다. `api/repos.py`와 `community.py`의 관계를 따른다.
- 기존 동작(레포 카드, 이슈 패널, 공용 레포 등록, 이름 검색)과 기존 테스트 기대값은 바꾸지 않는다.
- 작업 범위는 아래 0~5단계뿐이다. 다른 개선을 발견하면 구현하지 말고 완료 보고에 적는다.

## 현재 구조 요약 (2026-10-26 확인)

- `web.html`의 `refresh()`가 `/data.json`(9월 16일 정적 스냅샷)과 `/api/repos`를 같이 읽는다.
  Redis 스냅샷(`repobite:snapshot`)이 있으면 그것으로 `state`를 교체한다.
- `community_batch.py`가 스냅샷에 `items`, `collected_repos`, `collected_at`(UTC ISO)을 저장한다.
  화면은 지금 `collected_at`을 표시하지 않는다. 정적 `data.json`에는 `collected_at`이 없다.
- 추천 조건은 `web.html`의 `good(x)`이다: 판정 성공, `exclude=false`, `difficulty=1`, `readiness=ready`, `freshness.eligible=true`.
  지금은 이 이슈들이 정렬 기준으로만 쓰이고 따로 모여 보이지 않는다.
- `<title>`은 `Explore repositories | RepoBite`, `h1`은 `hidden`이다. `description`과 Open Graph 메타 태그가 없다.
- 방문 분석과 피드백 경로가 없다.

## 0단계. 사전 확인 (코드 변경 없음)

홍보 판단의 전제이므로 구현 전에 확인하고 결과를 완료 보고에 적는다.

1. 정식 주소에서 `/api/repos`를 조회해 `snapshot`이 `null`이 아닌지, `snapshot.collected_at`이 36시간 이내인지 확인한다.
2. Windows 홈서버의 정기 배치(`community_batch.py`) 최근 결과를 [홈서버 상태 문서](홈서버-상태.md)의 방법으로 확인한다.
3. 둘 중 하나라도 실패하면 1~5단계 구현은 계속하되, 완료 보고 맨 위에 "공개 데이터 갱신 중단"으로 표시한다.

## 1단계. 첫 화면 소개 문구

**바꿀 파일**: `web.html`, `test_web_ui.mjs`

- `<title>`을 `RepoBite | 초보자가 바로 손댈 수 있는 오픈소스 이슈`로 바꾼다.
- `main` 맨 위, 정렬·카테고리 바(`.bar`) 위에 소개 영역을 추가하고 기존 숨김 `h1`을 여기로 옮겨 표시한다.
  - `h1`: `처음 기여하기 좋은 오픈소스 이슈를 골라드립니다`
  - 설명: `라벨이 아니라 이슈 본문을 AI가 읽고, 범위가 작고 설명이 충분하며 아직 아무도 맡지 않은 이슈만 추천합니다.`
  - 용어 안내 한 줄: `쉬움: 수정 범위가 작고 위치가 분명함 · 바로 착수: 재현 방법이나 기대 결과가 본문에 있음 · 추천 직전 GitHub에서 닫힘·담당자·연결된 PR을 다시 확인`
  - 주의 한 줄: `AI 판정은 틀릴 수 있습니다. 작업 전에 판정 이유와 원문을 확인하세요.`
- 모바일(767px 이하)에서는 소개 영역 좌우 여백을 12px로 맞춘다. 가로 스크롤이 생기면 안 된다.
- `.bar`의 `position: sticky`가 소개 영역을 덮지 않는지 확인한다.

**완료 기준**: 데스크톱·모바일 폭에서 첫 화면 위쪽에 위 네 줄이 보인다. `test_web_ui.mjs`에 `title`과 `h1` 문구 검사를 추가한다.

## 2단계. 데이터 갱신 시각 표시

**바꿀 파일**: `web.html`, `test_web_ui.mjs`

- `state.collected_at`을 한국 시간으로 `10월 26일 09:00 수집`처럼 표시한다.
  `Intl.DateTimeFormat('ko-KR', {timeZone: 'Asia/Seoul', month: 'long', day: 'numeric', hour: '2-digit', minute: '2-digit', hour12: false})`를 쓴다.
- 위치는 3단계에서 만드는 추천 이슈 영역의 제목 오른쪽(모바일은 제목 아래)이다.
- `collected_at`이 없으면(정적 `data.json` 폴백) `수집 시각 미확인`으로 표시한다. 시각을 추정하거나 지어내지 않는다.
- 현재 시각 기준 36시간을 넘으면 문구 뒤에 `· 최근 수집이 지연되고 있습니다`를 붙인다. 기준은 홈서버 상태 페이지의 "오래됨" 기준과 같다.
- 날짜 해석에 실패하면 `수집 시각 미확인`으로 표시한다.
- `data.json`은 손으로 고치지 않는다.

**완료 기준**: 세 경우(정상, 36시간 초과, `collected_at` 없음)의 문구를 `test_web_ui.mjs`에서 vm 실행으로 검사한다. 현재 시각은 테스트에서 고정한다.

## 3단계. 추천 이슈 상단 배치

**바꿀 파일**: `web.html`, `test_web_ui.mjs`

- 소개 영역과 `사용자들이 추가한 레포` 섹션 사이에 `지금 손댈 만한 이슈` 섹션을 추가한다.
  제목 형식: `지금 손댈 만한 이슈 N건`. N은 현재 필터를 적용한 뒤의 건수다.
- 대상은 기존 `good(x)`를 통과한 `state.items` 전체다. 조건을 새로 만들지 않는다.
- 카테고리 칩과 검색어를 레포 카드와 같은 방식(`matches`)으로 적용한다.
- 정렬은 `created_at` 최신순이다. 건수 상한은 두지 않는다(실측상 하루 수 건 수준이다).
- 각 행에 표시: 레포 이름, 이슈 제목(GitHub 링크), 작성일(기존 `MM.DD` 형식), 판정 이유(`grade.reason`).
  링크는 기존 이슈 패널과 같은 방식으로 연다.
- 섹션 설명 문구: `작업 전에 이슈에 댓글로 작업 의사를 남기면 다른 기여자와 겹치지 않습니다.`
- 0건이면 `지금은 조건을 통과한 이슈가 없습니다. 아래 레포에서 '확인 필요' 이슈를 둘러보세요.`를 표시한다.
- 레포를 선택했을 때 열리는 이슈 패널과 기존 카드 렌더링(`cardCache`)은 그대로 둔다.

**완료 기준**: `test_web_ui.mjs`에서 vm 실행으로 추천 2건·비추천 1건 데이터를 넣고 다음을 검사한다. 추천 2건만 최신순으로 나오는지, 필터 적용 후 건수가 맞는지, 0건 문구가 나오는지.

## 4단계. 링크 미리보기

**바꿀 파일**: `web.html`, `og.png`(새 파일), `.vercelignore`, `test_web_ui.mjs`

- `head`에 추가한다.
  - `<meta name="description">`: 1단계 설명 문장
  - `og:type=website`, `og:site_name=RepoBite`, `og:url=https://repobite.vercel.app/`
  - `og:title`: 1단계 `<title>`과 같은 문구
  - `og:description`: 1단계 설명 문장
  - `og:image=https://repobite.vercel.app/og.png`, `og:image:width=1200`, `og:image:height=630`
  - `twitter:card=summary_large_image`
- `og.png`는 1200×630 PNG, 300KB 이하로 만든다. 배경은 화면과 같은 `#09090b`, 텍스트는 `RepoBite`와 1단계 `h1` 문구다.
  만드는 데 쓴 임시 HTML·스크립트는 커밋하지 않고 `og.png`만 커밋한다.
- `.vercelignore` 허용 목록에 `!og.png`를 추가한다.
- 미리보기 URL은 정식 주소 기준 절대 경로만 쓴다. 프리뷰 배포 주소를 넣지 않는다.

**완료 기준**: 메타 태그 존재를 `test_web_ui.mjs`에서 검사한다. 배포 후 정식 주소의 `/og.png`가 200과 `image/png`로 응답한다.

## 5단계. 반응 측정 (방문·클릭 집계와 피드백)

외부 분석 서비스는 쓰지 않는다. 이미 연결된 Upstash Redis에 일별 집계만 저장한다. 쿠키, IP, 사용자 식별자는 저장하지 않는다.

### 5-1. 저장 모듈 `metrics.py` (새 파일)

- `community.redis()`를 재사용한다. Redis 연결 코드를 복사하지 않는다.
- `record_event(name)`
  - 허용 이벤트는 `visit`, `featured_click`, `issue_click` 세 개다. 그 밖의 이름은 `ValueError`.
  - 키 `repobite:events:YYYY-MM-DD`(UTC 날짜) 해시에서 해당 필드를 1 증가시키고 만료를 90일로 설정한다.
  - 서비스 전체 시간당 3,000건을 넘으면 저장하지 않고 조용히 무시한다. `community.register`의 `EVAL` 카운터 방식을 따르고 키는 `repobite:event-rate`다.
- `record_feedback(text)`
  - 앞뒤 공백을 제거하고 1~500자만 받는다. 그 밖은 `ValueError`.
  - 서비스 전체 시간당 20건 제한. 넘으면 `OverflowError`(등록 API와 같은 429 처리).
  - `repobite:feedback` 리스트 앞에 `{"text", "created_at"}` JSON을 넣고 최근 500건만 남긴다.
  - 같은 날짜 해시의 `feedback` 필드도 1 증가시킨다.
- `event_counts(days)`와 `recent_feedback(limit)`: 아래 보고 스크립트용 조회 함수.

### 5-2. API 핸들러 `api/events.py`, `api/feedback.py` (새 파일)

- `api/repos.py`의 `handler`, `reply` 구조를 따른다. 공통 검사를 꺼낼 필요가 있으면 `community.py`에 작은 함수로 둔다.
- 둘 다 `POST`만 받는다. `Origin`이 `https://repobite.vercel.app`이 아니거나 `Content-Type`이 `application/json`이 아니면 403.
- 본문 크기 상한: 이벤트 256바이트, 피드백 2,048바이트.
- 이벤트: 성공·무시 모두 204. 입력 오류는 400. DB 오류도 204로 응답해 화면에 오류를 띄우지 않는다.
- 피드백: 성공 201, 입력 오류 400, 한도 초과 429, DB 오류 503. 오류 메시지는 기존 등록 API처럼 한국어로 쓴다.
- `.vercelignore`에 `!metrics.py`, `!api/events.py`, `!api/feedback.py`를 추가한다.

### 5-3. 화면 `web.html`

- `track(name)`: `fetch('/api/events', {method: 'POST', keepalive: true, headers: {'Content-Type': 'application/json'}, body})`.
  실패는 무시하고 화면 동작을 막지 않는다.
- `visit`: 페이지 로드 시 한 번. 같은 탭의 재방문 중복은 `sessionStorage`로 막는다. `sessionStorage` 접근은 `try/catch`로 감싸고, 실패하면 그냥 전송한다.
- `featured_click`: 3단계 추천 섹션의 이슈 링크 클릭.
- `issue_click`: 기존 이슈 패널의 이슈 링크 클릭.
- `의견 보내기` 버튼: 왼쪽 레일의 `+` 버튼 아래(모바일은 상단 `+ 담기` 옆)에 둔다. 기존 레포 등록 `dialog`와 같은 스타일의 대화상자를 연다.
  - `textarea`(최대 500자), 안내 `서비스에 대한 의견을 남겨주세요. 답장이 필요하지 않은 익명 의견이며 개인정보는 적지 마세요.`
  - 보내는 중에는 버튼을 잠근다. 성공하면 `의견을 보냈습니다. 고맙습니다.`를 보여주고 닫는다. 실패하면 입력을 유지하고 서버 오류 문구를 보여준다.

### 5-4. 운영자 보고 스크립트 `metrics_report.py` (새 파일, 배포 제외)

- `python3 metrics_report.py --days 14`: 날짜별 `visit`, `featured_click`, `issue_click`, `feedback` 표와 최근 피드백 20건을 Markdown으로 stdout에 출력한다.
- 환경변수 `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN`을 쓴다. `.vercelignore` 허용 목록에는 넣지 않는다.
- 피드백 본문은 텍스트 그대로 출력한다. 터미널 제어 문자는 제거한다.

### 5단계 테스트

- `test_metrics.py`(새 파일): `community.redis`를 `patch`해 이벤트 허용 목록, 시간당 상한 무시, 피드백 길이·429, 보관 500건 명령 인자, 조회 함수를 검사한다.
  API 핸들러의 Origin·Content-Type·본문 크기 거절도 검사한다.
- `test_web_ui.mjs`: `track` 호출 위치 세 곳, `keepalive`, 피드백 대화상자 성공·실패 분기를 검사한다.
- `.github/workflows/windows.yml`의 Python 테스트 목록에 `metrics`를 추가한다.

**완료 기준**: 로컬 테스트 전체 통과. 배포 후 정식 주소에서 방문 1회, 추천 링크 클릭 1회, 피드백 1건을 직접 보내고 `metrics_report.py`에 반영되는 것을 확인한다.
확인용 피드백은 확인 후 `LREM`으로 지우고, 그 사실을 보고에 적는다.

## 문서

- `README.md`의 "사용자들이 추가한 레포" 다음에 "반응 측정" 절을 추가한다. 저장 항목, 저장하지 않는 항목(쿠키·IP·식별자), 90일 만료, 시간당 상한, `metrics_report.py` 사용법을 적는다.

## 검증과 배포

1. `python3 test_radar.py`, `python3 test_web.py`, `python3 test_community.py`, `python3 test_metrics.py`, `python3 test_freshness.py`, `python3 test_vertex.py`, `python3 test_home_status.py`, `node test_web_ui.mjs`를 Python 3.14에서 모두 통과시킨다.
2. 로컬 `python3 web.py`가 기존처럼 동작하는지 확인한다. 로컬 웹은 `/api/events`·`/api/feedback`이 없으므로, 이 호출이 실패해도 화면 오류가 없어야 한다.
3. 배포와 검증은 `AGENTS.md` 규칙을 따른다. `vercel inspect https://repobite.vercel.app`으로 새 배포 ID를 확인하고, 정식 주소에서 HTML·`og.png`·`data.json`을 내려받아 검증한다.
4. 카카오톡 공유 미리보기는 [카카오 공유 디버거](https://developers.kakao.com/tool/debugger/sharing)에서 정식 주소의 캐시를 초기화한 뒤 확인한다.
